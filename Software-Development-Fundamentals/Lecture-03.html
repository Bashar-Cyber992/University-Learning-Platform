🎭 1. التجريد وإخفاء تفاصيل التنفيذ (Abstraction and Information Hiding)

1.1 ما معنى التجريد؟

التجريد (Abstraction): هو عملية إظهار المعلومات والوظائف المهمة للمستخدم أو للمكون البرمجي الآخر، وإخفاء التفاصيل الداخلية المعقدة التي لا يحتاج إلى معرفتها.

بمعنى أبسط: التجريد يعني أن تستخدم الشيء دون الحاجة إلى معرفة كيف يعمل من الداخل.

1.2 مثال من الحياة اليومية: قيادة السيارة (مخطط تفاعلي)

عندما تقود السيارة، أنت تحتاج إلى معرفة: كيفية تشغيل المحرك، استخدام المكابح، زيادة السرعة، وتغيير الاتجاه. لكن هل تحتاج إلى معرفة التفاصيل الداخلية لعمل المحرك والاحتراق ونظام حقن الوقود؟ لا! أنت تتعامل مع واجهة بسيطة، بينما تُخفى التفاصيل الداخلية المعقدة.

الشكل التوضيحي (1): السائق يتعامل مع واجهة القيادة البسيطة بينما تُخفى تفاصيل عمل المحرك الداخلية

1.3 مثال برمجي: دالة student.save()

لنفترض أننا نريد حفظ بيانات طالب. المستخدم (أو المطور الذي يستدعي الدالة) يحتاج فقط إلى استدعاء: student.save()، ولا يحتاج إلى معرفة كيفية الاتصال بقاعدة البيانات، أو كتابة أوامر SQL، أو تحويل البيانات، أو معالجة أخطاء التخزين على القرص.

student_abstraction.py — مثال التجريد في Python 
class Student:
    def __init__(self, name, university_id):
        self.name = name
        self.university_id = university_id

    def save(self):
        # تفاصيل الاتصال والتخزين مخفية هنا عن المستدعي
        print("تم حفظ بيانات الطالب")

# الاستخدام (واجهة بسيطة وواضحة):
student = Student("Ahmed", 101)
student.save()

1.4 ما الفرق بين التجريد (Abstraction) والتغليف (Encapsulation)؟

هذان المفهومان مرتبطان في البرمجة كائنية التوجه، لكنهما ليسا الشيء نفسه:

وجه المقارنة التجريد (Abstraction) التغليف (Encapsulation)
المعنى إظهار المهم وإخفاء التفاصيل غير الضرورية. تجميع البيانات والسلوك في وحدة واحدة والتحكم في الوصول.
التركيز ماذا يقدم المكون؟ (على مستوى التصميم). كيف نحمي بياناته وحالته الداخلية؟ (على مستوى التنفيذ).
الهدف تبسيط الاستخدام وتقليل التعقيد الذهني. حماية الحالة الداخلية من التعديل العشوائي أو الخاطئ.
المثال دالة save() أو deposit() كواجهة واضحة. جعل الرصيد __balance خاصاً ومنع تعديله إلا بشروط.
bank_encapsulation.py — مثال التغليف وحماية الحالة الداخلية 
class BankAccount:
    def __init__(self, balance):
        self.__balance = balance  # إخفاء الرصيد الداخلي

    def deposit(self, amount):
        if amount > 0:
            self.__balance += amount

    def get_balance(self):
        return self.__balance

ملاحظة أكاديمية دقيقة: استخدام شرطتين سفليتين (__balance) في Python يوفر آلية تشويه الأسماء (Name Mangling) لمنع الوصول العرضي المباشر، وليس حماية أمنية تشفيرية كاملة.

✨ لماذا نستخدم التجريد (6 فوائد)؟

  1. تقليل تعقيد البرنامج.
  2. تسهيل فهم الكود وقراءته.
  3. إخفاء التفاصيل غير الضرورية.
  4. تسهيل تغيير طريقة التنفيذ الداخلية لاحقاً.
  5. تحسين قابلية الاختبار.
  6. تمكين أكثر من مطور من العمل على أجزاء مختلفة بالتوازي.

💳 مثال تطبيقي: نظام دفع إلكتروني

يقدم النظام للمتجر واجهة موحدة بسيطة: payment.pay(100)، بينما قد تكون وسيلة الدفع الفعلية خلف الكواليس:

  • بطاقة بنكية (Credit/Debit Card).
  • محفظة إلكترونية (E-Wallet).
  • تحويل بنكي (Bank Transfer).
  • دفع نقدي (Cash).
  1. عرّف التجريد بأسلوبك: هو إظهار الوظائف والعمليات الأساسية التي يحتاجها المستخدم للتعامل مع المكون، وإخفاء التفاصيل الداخلية المعقدة لكيفية تنفيذها.
  2. اذكر مثالاً من الحياة اليومية على التجريد: قيادة السيارة؛ حيث يتعامل السائق مع المقود والدواسات فقط دون الحاجة لمعرفة آلية عمل غرفة الاحتراق وحقن الوقود داخل المحرك.
  3. لماذا نستخدم التجريد في البرمجة؟ لتقليل التعقيد، وتسهيل فهم الكود، وإخفاء التفاصيل غير الضرورية، وتسهيل تعديل التنفيذ الداخلي دون كسر بقية البرنامج، وتحسين الاختبار والعمل الجماعي.
  4. ما الفرق بين Abstraction وEncapsulation؟ التجريد يركز على تبسيط الواجهة وإظهار «ماذا» يفعل الكائن دون تفاصيله، بينما التغليف يركز على تجميع البيانات مع الدوال وحماية الحالة الداخلية والتحكم في الوصول إليها.
  5. هل يستطيع المستخدم الاستفادة من وظيفة برمجية دون معرفة تفاصيل تنفيذها؟ وضّح: نعم؛ فمثلاً عند استدعاء student.save() أو payment.pay(100) يحقق المستخدم النتيجة المطلوبة عبر الواجهة المعلنة دون معرفة أوامر SQL أو بروتوكولات الدفع الداخلية.
  6. كيف يساعد التجريد على تطوير البرنامج؟ يسمح بتغيير آلية التنفيذ الداخلية (مثلاً التحول من حفظ البيانات في ملف نصي إلى قاعدة بيانات) مع بقاء الواجهة ثابتة فلا تتأثر بقية الوحدات المستدعية.

🧱 2. الفئات والكائنات والواجهات والتكوين (Classes, Objects, Interfaces & Composition)

قبل دراسة مبادئ SOLID، لا بد من إتقان أربعة لبنات أساسية في البرمجة كائنية التوجه (OOP):

📐 الفئة (Class) — المخطط الهندسي

الفئة: هي قالب أو مخطط (Blueprint) نستخدمه لإنشاء كائنات تحتوي على بيانات (Attributes) وسلوك/وظائف (Methods).

class_example.py
class Student:
    def __init__(self, name, age):
        self.name = name   # البيانات (الاسم)
        self.age = age     # البيانات (العمر)

    def display(self):
        print(self.name, self.age)  # السلوك (عرض البيانات)

🏠 الكائن (Object) — النسخة الفعلية

الكائن: هو نسخة فعلية (Instance) تم إنشاؤها في الذاكرة من الفئة. التشبيه: الفئة مثل المخطط الهندسي للمنزل، والكائن هو المنزل الفعلي الذي بُني باستخدام هذا المخطط.

object_example.py
student1 = Student("Ahmed", 20)
student2 = Student("Ali", 22)

student1.display()
student2.display()

📜 الواجهة (Interface) — العقد البرمجي

الواجهة: تحدد الوظائف والعمليات التي يجب أن يوفرها مكون برمجي، دون أن تفرض تفاصيل التنفيذ الداخلية. مثلاً في نظام إرسال الإشعارات، نحدد عقداً موحداً يحتوي دالة send(message)، ثم نكتب تنفيذاً للبريد الإلكتروني وآخر للرسائل النصية.

interface_notification.py
from abc import ABC, abstractmethod

class Notification(ABC):
    @abstractmethod
    def send(self, message):
        pass

class EmailNotification(Notification):
    def send(self, message):
        print("Email:", message)

class SMSNotification(Notification):
    def send(self, message):
        print("SMS:", message)

🧩 التكوين (Composition) — بناء الكبير من أجزاء متخصصة

التكوين: يعني بناء كائن أو مكون كبير باستخدام كائنات أصغر تتعاون معه. فبدلاً من وضع جميع وظائف الجامعة في فئة واحدة ضخمة، نجعل لكل خدمة فئة متخصصة ثم نجمعها داخل UniversitySystem.

composition_university.py
class StudentService:
    def add_student(self):
        print("إضافة طالب")

class GradeService:
    def calculate_grade(self):
        print("حساب الدرجة")

class UniversitySystem:
    def __init__(self):
        self.students = StudentService()
        self.grades = GradeService()

system = UniversitySystem()
system.students.add_student()
system.grades.calculate_grade()

2.5 المقارنة المحورية: الوراثة (Inheritance) مقابل التكوين (Composition)

وجه المقارنة الوراثة (Inheritance) التكوين (Composition)
نوع العلاقة علاقة Is-A (نوع من) علاقة Has-A (يحتوي على)
المعنى التصميمي فئة فرعية تمثل نوعاً متخصصاً من فئة أساسية. مكون كبير يُبنى عبر احتواء مكونات أصغر متخصصة.
مثال جامعي طالب الدراسات العليا هو طالب (GraduateStudent is a Student). نظام الجامعة يحتوي على خدمة الطلاب وخدمة الدرجات.
المرونة ارتباط وثيق ثابت وقت التعريف. مرونة عالية وإمكانية تبديل المكونات الداخلية بسهولة.

📏 قاعدة تصميمية ذهبية

لا تستخدم الوراثة لمجرد إعادة استخدام الكود؛ استخدم التكوين عندما يكون أكثر ملاءمة للعلاقة بين المكونات! (وهو ما يُعرف في هندسة البرمجيات بمبدأ: Favor Composition over Inheritance).

  1. ما المقصود بالفئة؟ هي قالب أو مخطط برمجي يعرّف البيانات (الخصائص) والسلوك (الدوال) التي ستمتلكها الكائنات المنشأة منه.
  2. ما المقصود بالكائن؟ هو نسخة فعلية حقيقية تُنشأ في الذاكرة استناداً إلى قالب الفئة وتحمل قيماً محددة.
  3. ما الفرق بين Class وObject؟ الفئة هي المخطط النظري العام (مثل مخطط المنزل)، بينما الكائن هو التطبيق أو النسخة الفعلية المبنية من ذلك المخطط (مثل الطالب أحمد أو الطالب علي).
  4. ما وظيفة Interface؟ تحديد العقد البرمجي والعمليات المطلوبة من أي مكون يطبقها، دون فرض طريقة التنفيذ الداخلية، مما يتيح تعدد الأشكال وسهولة الاستبدال.
  5. لماذا نستخدم Composition؟ لبناء أنظمة كبيرة ومعقدة عبر تجميع وحدات صغيرة متخصصة، مما يمنع تضخم الفئات ويزيد المرونة وقابلية الصيانة.
  6. ما الفرق بين Inheritance وComposition؟ الوراثة تعبر عن علاقة «نوع من» (Is-A) وتربط الفئة الفرعية بالأصل ارتباطاً وثيقاً، بينما التكوين يعبر عن علاقة «يحتوي على» (Has-A) ويبني المكون عبر تعاون كائنات مستقلة.
  7. أعط مثالاً على واجهة برمجية في نظام إدارة الطلاب: واجهة StudentRepository التي تحدد دالة save(student)، وتنفذها فئات مختلفة مثل MySQLRepository وFileRepository.

🏗️ 4. هندسة التطبيقات متعددة الطبقات وفصل الاهتمامات (Layered Architecture & SoC)

من أهم الأساليب المعمارية في بناء التطبيقات الكبيرة تقسيم النظام أفقياً إلى ثلاث طبقات رئيسية، بحيث يكون لكل طبقة دور واضح ولا تتجاوز حدودها:

1️⃣ طبقة العرض (Presentation Layer)

الطبقة التي يتفاعل معها المستخدم مباشرة. وظيفتها استقبال المدخلات وعرض النتائج فقط (مثل: صفحة تسجيل الطالب، شاشة تسجيل الدخول، شاشة الدرجات، لوحة التحكم).

2️⃣ طبقة منطق العمل (Business Logic Layer)

تضم القواعد والسياسات التي تحكم عمل النظام (مثل: منع تسجيل طالب لم يستوفِ المتطلب السابق، منع التسجيل في مقرر ممتلئ، التحقق من أن الدرجة ضمن النطاق المسموح).

3️⃣ طبقة الوصول إلى البيانات (Data Access Layer)

تتولى تخزين البيانات واسترجاعها وتحديثها فقط (مثل التعامل مع MySQL، PostgreSQL، SQLite، ملفات JSON، أو خدمات التخزين الخارجية).

🔄 محاكي رحلة تسجيل طالب في مقرر عبر الطبقات الثلاث

اضغط على كل خطوة لتتبع كيف ينتقل الطلب من واجهة المستخدم إلى قاعدة البيانات ويعود بالنتيجة:

الشكل التوضيحي (2): المعمارية متعددة الطبقات (3-Tier Layered Architecture)

💡 لماذا نفصل الطبقات؟ ومبدأ فصل الاهتمامات (Separation of Concerns)

لنفترض أن الجامعة كانت تستخدم ملفات Excel لتخزين البيانات، ثم قررت الانتقال إلى قاعدة بيانات PostgreSQL. إذا كان البرنامج مصمماً بطبقات مفصولة، نستبدل مكون طبقة الوصول إلى البيانات فقط دون تغيير شاشات البرنامج أو قواعد التسجيل!

فصل الاهتمامات (Separation of Concerns - SoC): مبدأ تصميمي يعني أن كل جزء من النظام يهتم بمشكلة أو مسؤولية واحدة محددة؛ فلا ينبغي أن تحتوي شاشة تسجيل الطالب على أوامر SQL وقواعد التسجيل وحسابات الرسوم معاً.

  1. ما المقصود بالطبقات البرمجية؟ تقسيم النظام البرمجي إلى مستويات متدرجة (العرض، منطق العمل، الوصول للبيانات)، لكل مستوى مسؤولية محددة ويتواصل مع الطبقة المجاورة بوضوح.
  2. ما وظيفة Presentation Layer؟ التفاعل المباشر مع المستخدم: عرض الواجهات واستقبال المدخلات وإظهار النتائج أو رسائل الخطأ دون تنفيذ قواعد عمل معقدة أو أوامر قاعدة بيانات.
  3. ما وظيفة Business Logic Layer؟ احتواء وتطبيق قواعد العمل والسياسات (مثل التحقق من المتطلبات السابقة، سعة المقرر، ونطاق الدرجات).
  4. ما وظيفة Data Access Layer؟ تنفيذ عمليات القراءة والكتابة والتحديث والحذف على وسائط التخزين وقواعد البيانات وعزل تفاصيلها عن بقية النظام.
  5. وضّح كيف يساعد فصل الطبقات في تغيير قاعدة البيانات: لأن طبقة الوصول للبيانات معزولة عن منطق العمل والعرض، يمكن استبدال ملفات Excel أو MySQL بـ PostgreSQL في طبقة البيانات فقط دون تعديل الشاشات أو قواعد التسجيل.
  6. ما المقصود بـ Separation of Concerns؟ مبدأ هندسي يقضي بتقسيم البرنامج إلى أجزاء متميزة بحيث يعالج كل جزء جانباً واحداً من المشكلة (العرض، المنطق، التخزين) دون تداخل.
  7. ارسم معمارية نظام إدارة الطلاب: يتكون من طبقة العرض (شاشات التسجيل والدرجات) ← تتصل بطبقة منطق العمل (خدمات الطلاب والتسجيل والدرجات) ← تتصل بطبقة الوصول للبيانات (مستودعات البيانات وقاعدة البيانات).

💎 5. مبادئ SOLID الخمسة في التصميم كائني التوجه

ما معنى SOLID؟ هي كلمة مختصرة (Acronym) تجمع الحروف الأولى لخمسة مبادئ تصميمية جوهرية في البرمجة كائنية التوجه (OOP)، صاغها وشرحها في صورتها المشهورة المهندس والكاتب الأمريكي Robert C. Martin (Uncle Bob) في كتابه المرجعي Agile Software Development: Principles, Patterns, and Practices.

5.6 ملخص مبادئ SOLID وطريقة حفظها والملاحظة الأكاديمية

الرمز المبدأ بالإنجليزية الترجمة العربية الفكرة الأساسية قاعدة الحفظ السريعة
S Single Responsibility المسؤولية الواحدة مسؤولية واحدة واضحة (سبب واحد للتغيير). لا تجمع مسؤوليات مختلفة في فئة واحدة.
O Open/Closed الانفتاح والإغلاق مفتوح للإضافة ومغلق أمام التعديل غير الضروري. أضف وظائف جديدة دون العبث بالكود المستقر.
L Liskov Substitution ليسكوف للاستبدال الفئة الفرعية بديل صحيح للفئة الأساسية. لا تجعل الوراثة تكسر السلوك المتوقع.
I Interface Segregation فصل الواجهات واجهات صغيرة ومتخصصة بدل واجهة ضخمة. لا تجبر المكون على وظائف لا يحتاج إليها.
D Dependency Inversion عكس الاعتماديات الاعتماد على التجريدات لا تفاصيل التنفيذ. لا تربط منطقك الأساسي بتفاصيل التنفيذ.

🎓 ملاحظة أكاديمية مهمة حول تطبيق SOLID

مبادئ SOLID إرشادية (Guidelines / Heuristics) وليست قوانين جامدة يجب تطبيقها حرفياً على كل فئة أو برنامج صغير! فالإفراط في تطبيقها في مواضع بسيطة لا تحتاج إليها قد يؤدي إلى تعقيد غير مبرر (Over-Engineering) وكثرة الملفات والواجهات بلا فائدة حقيقية.

🔗 6. تقليل الترابط وزيادة التماسك (Low Coupling and High Cohesion)

يُعدّ هذان المفهومان من أهم مقاييس جودة التصميم المعماري في هندسة البرمجيات:

1️⃣ الترابط (Coupling) — العلاقة بين الوحدات

التعريف: مقدار اعتماد وحدة برمجية على وحدة أخرى.

  • ترابط مرتفع (Tight Coupling): إذا اعتمدت StudentService مباشرة على MySQLDatabase؛ فأي تغيير في قاعدة البيانات يكسر الخدمة.
  • ترابط منخفض (Loose Coupling): تتعامل الخدمة مع واجهة عامة للتخزين دون معرفة نوع القاعدة الفعلية.

2️⃣ التماسك (Cohesion) — الترابط داخل الوحدة

التعريف: مدى ارتباط الوظائف والمسؤوليات الموجودة داخل الوحدة الواحدة بهدف مشترك.

🏆 القاعدة الذهبية لجودة التصميم البرمجي

Low Coupling + High Cohesion = Better Software Design

أي: ترابط أقل بين الوحدات + تماسك أعلى داخل كل وحدة.

  1. عرّف Coupling: هو درجة ومقدار اعتماد وحدة برمجية على تفاصيل وحدة برمجية أخرى.
  2. عرّف Cohesion: هو مدى ارتباط وتكامل الوظائف والمسؤوليات الموجودة داخل الوحدة البرمجية الواحدة لخدمة هدف واحد محدد.
  3. ما الفرق بينهما؟ الترابط يقيس العلاقة الاعتمادية بين وحدتين أو أكثر ونسعى لتقليله، بينما التماسك يقيس انسجام المهام داخل الوحدة نفسها ونسعى لزيادته.
  4. لماذا نسعى إلى تقليل الترابط؟ لكي نتمكن من تعديل أو استبدال أي وحدة دون إجبار بقية وحدات النظام على التغيير، ولتسهيل الاختبار المستقل.
  5. لماذا نزيد التماسك؟ لجعل كل وحدة متخصصة، سهلة الفهم، سهلة الصيانة، وقابلة لإعادة الاستخدام دون حمل وظائف غريبة عنها.
  6. حلّل تصميم فئة تجمع (تسجيل الطالب + حساب فاتورة الكهرباء + إدارة الشبكة): هذا تصميم منخفض التماسك (Low Cohesion) ومخالف لـ SRP؛ لأن الوظائف لا يجمعها هدف مشترك، ويجب فصلها إلى وحدات مستقلة.

💉 7. حقن الاعتماديات (Dependency Injection - DI)

7.1 ما المقصود بحقن الاعتماديات؟

حقن الاعتماديات (Dependency Injection - DI): هو أسلوب تصميم وتنفيذ يتم فيه تمرير المكونات والخدمات التي تحتاج إليها الفئة من الخارج بدلاً من أن تقوم الفئة بإنشائها بنفسها في داخلها (new / MySQLDatabase()).

❌ بدون حقن الاعتماديات (إنشاء داخلي مقيد)

tight_service.py
class StudentService:
    def __init__(self):
        # الخدمة تنشئ قاعدة البيانات بنفسها!
        self.database = MySQLDatabase()

✅ مع حقن الاعتماديات (تمرير خارجي مرن)

injected_service.py
class StudentService:
    def __init__(self, database):
        # يتم حقن الاعتمادية من الخارج
        self.database = database
الشكل التوضيحي (3): آلية عمل حقن الاعتماديات (Dependency Injection)

7.2 أنواع حقن الاعتماديات الثلاثة والاختبار الوهمي (FakeRepository)

أولاً: Constructor Injection — يتم تمرير الاعتمادية عبر دالة البناء (__init__)، وهو الخيار الأنسب والأكثر شيوعاً عندما تكون الاعتمادية ضرورية لعمل الكائن منذ لحظة إنشائه.

class StudentService:
    def __init__(self, repository):
        self.repository = repository

ثانياً: Setter Injection — يتم تمرير الاعتمادية أو تبديلها بعد إنشاء الكائن من خلال دالة إعداد مخصصة، ويفيد عندما تكون الاعتمادية اختيارية أو قابلة للتغيير أثناء عمر الكائن.

class StudentService:
    def set_repository(self, repository):
        self.repository = repository

ثالثاً: Interface Injection — توفر الاعتمادية عبر واجهة أو عقد صريح يحدد دالة الحقن (مثل واجهة RepositoryInjectable)، وهو أقل شيوعاً في التطبيقات الحديثة مقارنة بحقن المنشئ وحقن الإعداد.

class RepositoryInjectable(ABC):
    @abstractmethod
    def inject_repository(self, repository):
        pass

كيف يساعد DI على الاختبار؟ نمرر قاعدة بيانات حقيقية في الإنتاج، ونمرر مستودعاً وهمياً (FakeRepository) في الاختبار للتحقق من منطق التسجيل دون الحاجة لاتصال فعلي بقاعدة بيانات!

class FakeRepository:
    def save(self, student):
        print("Fake save")

repository = FakeRepository()
service = StudentService(repository)

7.3 الفرق الدقيق بين مبدأ DIP وتقنية DI

وجه المقارنةعكس الاعتماديات (DIP)حقن الاعتماديات (DI)
التصنيفمبدأ تصميم معماري (حرف D في SOLID).أسلوب تنفيذ ونمط برمجي (Pattern / Technique).
الوظيفةيحدد اتجاه الاعتماديات (الاعتماد على التجريدات).يوفر ويمرر الاعتماديات من الخارج عملياً.
العلاقةيُستخدم DI كآلية عملية لتطبيق مبدأ DIP وتحقيق Low Coupling.
  1. ما المقصود بـ Dependency Injection؟ أسلوب برمجي تُمرَّر فيه التبعيات التي تحتاجها الفئة من الخارج (عبر المنشئ أو دالة إعداد) بدلاً من إنشائها داخل الفئة نفسها.
  2. لماذا نمرر الاعتماديات بدل إنشائها داخل الفئة؟ لتقليل الترابط، وتسهيل تبديل التنفيذ (مثل تغيير قاعدة البيانات) دون تعديل الخدمة، وتمكين حقن مكونات وهمية أثناء الاختبار.
  3. اذكر أنواع DI: (1) حقن المنشئ Constructor Injection، (2) حقن الإعداد Setter Injection، (3) حقن الواجهة Interface Injection.
  4. ما الفرق بين DIP وDI؟ DIP مبدأ معماري يفرض الاعتماد على التجريدات لا التفاصيل، بينما DI تقنية تنفيذية لتمرير الكائنات المعتمدة من الخارج.
  5. كيف نستخدم Fake Repository في الاختبار؟ ننشئ فئة وهمية تطبق واجهة المستودع وتخزن البيانات في قائمة في الذاكرة بدلاً من قاعدة بيانات حقيقية، ثم نحقنها داخل StudentService لاختبار قواعد التسجيل بسرعة وعزل تام.
  6. لماذا يُعتبر Constructor Injection خياراً جيداً في حالات كثيرة؟ لأنه يضمن عدم إنشاء الكائن في حالة ناقصة، ويوضّح جميع تبعياته الإلزامية في توقيع المنشئ، ويسمح بجعل الحقل ثابتاً بعد التهيئة.

🧪 8. الاختبار وإعادة هيكلة الكود (Testing and Refactoring)

1️⃣ أنواع الاختبار البرمجي (Software Testing)

التحقق المنهجي من أن البرنامج يعمل وفق المتطلبات المتوقعة:

  • اختبار الوحدة (Unit Testing): اختبار دالة أو وحدة منفردة بمعزل عن البقية.
  • اختبار التكامل (Integration Testing): اختبار تعاون أكثر من وحدة معاً (مثل الخدمة مع المستودع).
  • اختبار القبول (Acceptance Testing): التحقق من استيفاء النظام لمتطلبات المستخدم النهائي.

2️⃣ مثال Unit Test لدالة حساب المعدل

test_average.py
def calculate_average(grades):
    return sum(grades) / len(grades)

def test_average():
    assert calculate_average([80, 90, 100]) == 90

♻️ ما المقصود بإعادة الهيكلة (Refactoring)؟ وعلاقتها بـ SOLID

إعادة الهيكلة (Refactoring): هي تحسين البنية الداخلية للكود (مثل تقسيم فئة ضخمة إلى فئات متخصصة أو إزالة التكرار) دون تغيير سلوكه الخارجي المتوقع أو نتائجه.

العلاقة بين SOLID والاختبار: كلما كانت الوحدات مستقلة وتعتمد على واجهات واضحة وتستقبل تبعياتها عبر DI، أصبح استبدال قاعدة البيانات بمستودع وهمي (FakeRepository) واختبار منطق العمل في أجزاء من الثانية أمراً يسيراً، وتُشكّل تلك الاختبارات شبكة أمان تحمينا أثناء إعادة الهيكلة!

  1. عرّف Unit Testing: هو اختبار برمجي يفحص أصغر وحدة قابلة للاختبار في البرنامج (مثل دالة أو فئة منفردة) للتأكد من صحة منطقها بمعزل عن بقية النظام.
  2. ما الفرق بين Unit Testing وIntegration Testing؟ اختبار الوحدة يفحص وحدة منفردة بمعزل عن تبعياتها الخارجية، بينما اختبار التكامل يفحص تفاعل وتعاون عدة وحدات معاً (مثل طبقة الخدمة مع طبقة البيانات).
  3. ما المقصود بـ Refactoring؟ إعادة تنظيم وتحسين البنية الداخلية للشيفرة لتصبح أوضح وأسهل صيانة، مع الحفاظ التام على سلوكها ونتائجها الخارجية دون تغيير.
  4. هل يجب أن تغير إعادة الهيكلة نتائج البرنامج؟ لا؛ بل يُشترط أن تظل المخرجات والسلوك الخارجي مطابقين تماماً لما قبل إعادة الهيكلة.
  5. كيف تساعد مبادئ SOLID على اختبار البرامج؟ لأنها تفصل المسؤوليات (SRP) وتُبعد المنطق عن تفاصيل التنفيذ عبر واجهات (DIP/ISP)، مما يسمح بحقن كائنات وهمية (Fakes/Mocks) واختبار المنطق بسهولة دون قواعد بيانات حقيقية.

student_system_solid.py
from abc import ABC, abstractmethod

class Student:
    def __init__(self, student_id, name):
        self.student_id = student_id
        self.name = name

class StudentRepository(ABC):
    @abstractmethod
    def save(self, student):
        pass

class MySQLRepository(StudentRepository):
    def save(self, student):
        print("Saving to MySQL:", student.name)

class FileRepository(StudentRepository):
    def save(self, student):
        print("Saving to file:", student.name)

class StudentService:
    def __init__(self, repository):
        self.repository = repository

    def register_student(self, student):
        if not student.name:
            raise ValueError("Student name is required")
        self.repository.save(student)

class StudentReport:
    def generate(self, student):
        return f"Student: {student.name}"

# الاختبار باستخدام FakeRepository:
class FakeRepository(StudentRepository):
    def __init__(self):
        self.saved_students = []
    def save(self, student):
        self.saved_students.append(student)

📚 12. أسئلة شاملة للدرس (20 سؤالاً مع الإجابات النموذجية)

اختبر قدرتك على الإجابة عن الأسئلة العشرين الشاملة الواردة في المحاضرة، ثم افتح الإجابات النموذجية لمراجعة تحصيلك:

  1. اشرح مفهوم التجريد مع مثال برمجي: هو إظهار الوظائف الأساسية وإخفاء تفاصيل التنفيذ المعقدة؛ مثل استدعاء student.save() دون معرفة تفاصيل الاتصال بقاعدة البيانات وأوامر SQL.
  2. ما الفرق بين التجريد والتغليف؟ التجريد يبسط الواجهة ويركز على «ماذا» يقدمه المكون، بينما التغليف يجمع البيانات والسلوك ويحمي الحالة الداخلية من الوصول المباشر (مثل __balance).
  3. ما الفرق بين الفئة والكائن؟ الفئة (Class) هي القالب أو المخطط العام، أما الكائن (Object) فهو النسخة الفعلية المنشأة من ذلك القالب ببيانات محددة.
  4. ما أهمية الواجهات في التصميم البرمجي؟ تحدد العقد والعمليات المطلوبة دون فرض طريقة التنفيذ، مما يسمح بتعدد التنفيذات وسهولة استبدال المكونات وتقليل الترابط.
  5. اشرح الفرق بين الوراثة والتكوين: الوراثة تمثل علاقة «نوع من» (Is-A)، بينما التكوين يمثل علاقة «يحتوي على» (Has-A) ويبني مكونات كبيرة من كائنات أصغر متخصصة بمرونة أعلى.
  6. ما المقصود بالتصميم المعياري؟ تقسيم البرنامج إلى وحدات (Modules) مستقلة نسبياً تؤدي كل منها وظيفة واضحة وتتعاون لإنجاز النظام الكامل.
  7. ما أهمية تقسيم التطبيق إلى طبقات؟ يسهل الصيانة، ويحصر أثر التغييرات (مثل تغيير قاعدة البيانات من Excel إلى PostgreSQL دون تعديل الشاشات)، وينظم العمل الجماعي.
  8. ما الفرق بين طبقة العرض وطبقة منطق العمل؟ طبقة العرض مسؤولة عن واجهات المستخدم واستقبال المدخلات وعرض النتائج، بينما طبقة منطق العمل تطبق القواعد والشروط والعمليات الحسابية للنظام.
  9. اشرح مبادئ SOLID الخمسة: (S) المسؤولية الواحدة، (O) الانفتاح للإضافة والإغلاق أمام التعديل، (L) إمكانية استبدال الأنواع الفرعية، (I) فصل الواجهات إلى واجهات صغيرة متخصصة، (D) عكس الاعتماديات بالاعتماد على التجريدات.
  10. أعط مثالاً على مخالفة SRP وكيفية إصلاحها: فئة Student تجمع البيانات والتخزين وإرسال البريد وإصدار التقارير؛ وتُصلح بفصلها إلى Student وStudentRepository وEmailService وStudentReport.
  1. كيف يساعد OCP على إضافة وظائف جديدة؟ عبر تعريف تجريد أو واجهة ثابتة (مثل Discount) وإضافة فئات جديدة ترثها أو تطبقها (مثل EmployeeDiscount) دون تعديل الكود المستقر الموجود.
  2. ما المشكلة التي يعالجها LSP؟ يمنع الوراثة الخاطئة التي تجعل الفئة الفرعية تكسر توقعات الفئة الأساسية (مثل وراثة حساب ودائع ثابتة لا يقبل السحب من حساب بنكي يفترض إمكانية السحب).
  3. لماذا نستخدم واجهات صغيرة وفق ISP؟ حتى لا يُجبر أي مكون برمجي على تنفيذ دوال لا يحتاج إليها ولا يملك معنى لها.
  4. اشرح DIP مع مثال من نظام إدارة الطلاب: جعل StudentService (عالية المستوى) تعتمد على واجهة StudentRepository بدلاً من الاعتماد المباشر على MySQLDatabase.
  5. ما الفرق بين Coupling وCohesion؟ الترابط (Coupling) يقيس اعتماد وحدة على أخرى ونسعى لتقليله، بينما التماسك (Cohesion) يقيس ترابط الوظائف داخل الوحدة الواحدة ونسعى لزيادته.
  6. ما المقصود بحقن الاعتماديات؟ تمرير المكونات المعتمدة إلى الفئة من الخارج (عبر المنشئ أو دالة إعداد) بدلاً من إنشائها داخلياً.
  7. ما الفرق بين DIP وDI؟ DIP مبدأ معماري يوجه الاعتماد نحو التجريدات، أما DI فهو أسلوب تنفيذ عملي لتمرير تلك الاعتماديات من الخارج.
  8. كيف يساعد DI على اختبار البرنامج؟ يسمح بتمرير مستودع وهمي (FakeRepository) أثناء الاختبار بدلاً من قاعدة البيانات الحقيقية.
  9. ما المقصود بإعادة الهيكلة؟ تحسين البنية الداخلية للكود وتنظيفه دون تغيير سلوكه الخارجي أو مخرجاته.
  10. صمّم تطبيقاً يحقق مبدأ تقليل الترابط وزيادة التماسك: يُقسّم نظام إدارة المهام إلى: نموذج Task، واجهة تخزين TaskRepository (مع تنفيذ SQLiteTaskRepo وInMemoryTaskRepo)، وخدمة متماسكة TaskService تستقبل المستودع عبر Constructor Injection.

  8. الطبقات تفصل العرض عن منطق العمل والتخزين.
  9. SRP يعني مسؤولية واحدة واضحة.
  10. OCP يعني الانفتاح للإضافة والإغلاق أمام التعديل غير الضروري.
  11. LSP يعني إمكانية استبدال النوع الأساسي بالنوع الفرعي دون كسر السلوك المتوقع.
  12. ISP يعني استخدام واجهات صغيرة ومتخصصة.
  13. DIP يعني اعتماد الوحدات على التجريدات بدل تفاصيل التنفيذ.
  14. Coupling هو الترابط بين الوحدات.
  15. Cohesion هو تماسك المسؤوليات داخل الوحدة.
  16. DI يعني تمرير الاعتماديات من الخارج.
  17. الاختبارات تساعد على التأكد من صحة عمل الوحدات.
  18. Refactoring يحسن بنية الكود دون تغيير سلوكه المتوقع.

⭐ أهم قاعدة في المحاضرة: صمّم برامجك بحيث تكون سهلة الفهم، وسهلة الاختبار، وسهلة التغيير، وقابلة للتوسع دون تعقيد غير ضروري.

🗂️ بطاقات الاستذكار التفاعلية (12 بطاقة — انقر لقلب البطاقة)

Abstraction
(التجريد)انقر لقلب البطاقة ↺
إظهار المعلومات والوظائف المهمة للمستخدم وإخفاء التفاصيل الداخلية المعقدة للتنفيذ.
Abstraction vs. Encapsulationانقر لقلب البطاقة ↺
التجريد: يركز على «ماذا» يقدم الكائن.
التغليف: يجمع البيانات مع الدوال ويحمي الحالة الداخلية.
Composition vs. Inheritanceانقر لقلب البطاقة ↺
Composition (Has-A): بناء مكون من أجزاء متخصصة.
Inheritance (Is-A): نوع متخصص من فئة أصل.
Modularity & SoC
(المعيارية وفصل الاهتمامات)انقر لقلب البطاقة ↺
تقسيم النظام إلى وحدات مستقلة ذات مسؤوليات محددة تتعاون عبر واجهات واضحة.
Layered Architecture
(الطبقات الثلاث)انقر لقلب البطاقة ↺
1. طبقة العرض (Presentation)
2. طبقة منطق العمل (Business Logic)
3. طبقة البيانات (Data Access)
S — Single Responsibility
(SRP)انقر لقلب البطاقة ↺
يجب أن يكون لكل فئة مسؤولية واحدة واضحة أو سبب واحد رئيسي للتغيير.
O — Open/Closed Principle
(OCP)انقر لقلب البطاقة ↺
الوحدات البرمجية مفتوحة للإضافة والتوسعة، ومغلقة أمام التعديلات غير الضرورية في الكود المستقر.
L — Liskov Substitution
(LSP)انقر لقلب البطاقة ↺
إمكانية استبدال كائن من الفئة الأساسية بكائن من الفئة الفرعية دون كسر السلوك المتوقع.
I — Interface Segregation
(ISP)انقر لقلب البطاقة ↺
تقسيم الواجهات الضخمة إلى واجهات صغيرة ومتخصصة حتى لا يُجبر المكون على وظائف لا يحتاجها.
D — Dependency Inversion
(DIP)انقر لقلب البطاقة ↺
اعتماد الوحدات عالية ومنخفضة المستوى على التجريدات والواجهات بدلاً من تفاصيل التنفيذ المباشرة.
Low Coupling + High Cohesionانقر لقلب البطاقة ↺
ترابط أقل بين الوحدات المختلفة + تماسك أعلى للمسؤوليات داخل الوحدة الواحدة.
Dependency Injection (DI)
& Refactoringانقر لقلب البطاقة ↺
DI: تمرير الاعتماديات من الخارج.
Refactoring: تحسين بنية الكود دون تغيير سلوكه الخارجي.
