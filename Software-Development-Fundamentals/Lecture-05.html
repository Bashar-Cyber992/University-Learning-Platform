🔍 1. ما المقصود بالاختبار البرمجي (Software Testing)؟

1.1 مقدمة تمهيدية وتعريف علمي

تخيّل أنك كلّفت مبرمجاً ببناء نظام تسجيل الطلاب في الجامعة يشمل وظائف: إضافة طالب، حذف طالب، تسجيل الطالب في مقرر، حساب الرسوم الدراسية، وعرض الدرجات. بعد انتهاء البرمجة، لا يمكننا افتراض عمل البرنامج بصورة صحيحة؛ إذ قد يقبل تسجيل طالب في مقرر ممتلئ، أو يحسب الرسوم خطأً، أو يكرر التسجيل، أو ينهار عند إدخال رقم سالب.

📌 التعريف العلمي للاختبار البرمجي (Software Testing)

الاختبار البرمجي: هو عملية منهجية لتقييم البرنامج والتحقق من سلوكه الفعلي مقارنة بالسلوك المتوقع، بهدف اكتشاف العيوب (Defects)، وتقليل مخاطر الفشل، والتحقق من استيفاء النظام للمتطلبات المحددة بدقة.

1.2 لماذا نحتاج إلى الاختبار البرمجي؟ (7 مشكلات يحمي منها الاختبار)

المشكلة المحتملة في النظامالدور الوقائي للاختبار البرمجي
1. أخطاء الحساب المالي والأكاديميالتحقق من صحة المعادلات والنتائج الرقمية (مثل الرسوم والمعدلات).
2. فقدان البيانات أو تلفهااختبار عمليات الحفظ والتحديث والاسترجاع في قاعدة البيانات.
3. توقف النظام المفاجئ (Crash)اكتشاف حالات الفشل والاستثناءات عند المدخلات غير المتوقعة.
4. تكرار التسجيل أو تجاوز السعةاختبار قواعد العمل (Business Rules) والقيود المنطقية.
5. بطء النظام تحت الضغطقياس زمن الاستجابة والأداء (Performance) مع تعدد المستخدمين.
6. اختراق النظام أو تسرب الدرجاتاختبار الأمان (Security) وصلاحيات الوصول (Authorization).
7. تعطل ميزة قديمة بعد تحديث جديدتنفيذ اختبارات الانحدار (Regression Testing) لضمان استقرار النظام.

1.3 التمييز الجوهري بين الخطأ (Error) والعيب (Bug) والفشل (Failure)

وفق معايير هندسة البرمجيات (ISTQB)، يمثل هذا الثلاثي سلسلة سببية متتابعة يجب عدم الخلط بين عناصرها:

السلسلة السببية لجودة البرمجيات: من الخطأ البشري إلى العيب الكامن ثم الفشل الظاهر عند التنفيذ

📐 المثال الرياضي التطبيقي (حساب رسوم الطالب الجامعي)

المعادلة الصحيحة المطلوبة لحساب الرسوم الدراسية هي:

$$\text{Fees} = \text{CreditHours} \times \text{PricePerHour}$$

لكن المبرمج ارتكب سهواً وكتب في الشيفرة:

$$\text{Fees} = \text{CreditHours} + \text{PricePerHour}$$
  • الخطأ (Error): سهو المبرمج أو سوء فهمه عند كتابة المعادلة.
  • العيب (Defect / Bug): وجود السطر الخاطئ Fees = CreditHours + PricePerHour داخل ملف البرنامج.
  • الفشل (Failure): عندما يسجّل الطالب 3 ساعات بسعر 100$ ويُخرج النظام له فاتورة بقيمة 103$ بدلاً من 300$.
🌐 إثراء علمي — مبدأ ISTQB الأول

هل الاختبار يثبت خلو البرنامج تماماً من الأخطاء؟
لا! القاعدة العلمية الشهيرة في هندسة البرمجيات (Dijkstra & ISTQB Principle 1) تنص على أن: «الاختبار يثبت وجود العيوب، ولا يستطيع إثبات خلو البرنامج منها تماماً»؛ لأن عدد مدخلات ومسارات البرنامج الحقيقي شبه لا نهائي، لذا نهدف إلى تقليل احتمالية بقاء العيوب إلى الحد الأدنى المقبول.

  1. عرّف الاختبار البرمجي: هو عملية تقييم البرنامج والتحقق من سلوكه بهدف اكتشاف العيوب والتحقق من استيفائه للمتطلبات المحددة.
  2. لماذا لا يكفي تشغيل البرنامج مرة واحدة؟ لأن التشغيل لمرة واحدة ببيانات عادية يختبر مساراً واحداً فقط ولا يكشف الحالات الحدية، المدخلات الخاطئة، ضغط المستخدمين، أو الآثار الجانبية للتعديلات اللاحقة.
  3. وضّح الفرق بين Error و Bug و Failure: Error خطأ بشري يرتكبه المبرمج؛ Bug/Defect خلل ناتج داخل الشيفرة؛ Failure سلوك غير صحيح يظهر للمستخدم عند تنفيذ تلك الشيفرة.
  4. اذكر خمسة أهداف للاختبار البرمجي: (1) التحقق من صحة الحسابات، (2) منع فقدان البيانات، (3) اكتشاف حالات توقف النظام، (4) فرض قواعد العمل ومنع التكرار، (5) قياس الأداء والأمان وضمان عدم تعطل الميزات القديمة.
  5. هل الاختبار يثبت خلو البرنامج من الأخطاء؟ وضح إجابتك: لا، الاختبار يثبت وجود العيوب ويزيد الثقة في الجودة، لكن استحالة تجربة جميع المدخلات والظروف الممكنة تجعل إثبات الخلو المطلق من العيوب أمراً غير ممكن عملياً.

🤖 2. الاختبار اليدوي (Manual) والاختبار الآلي (Automated)

👤 2.1 الاختبار اليدوي (Manual Testing)

هو أن يقوم إنسان (مختبر جودة أو مطور) بتشغيل البرنامج بنفسه، وإدخال البيانات عبر الواجهة، ومراقبة النتائج بعينيه للحكم على نجاح العملية.

مثال: يفتح الموظف بوابة الجامعة، يكتب اسم الطالب ورقمه، يضغط زر «تسجيل»، ويتحقق بصرياً من ظهور رسالة النجاح.

⚙️ 2.2 الاختبار الآلي (Automated Testing)

هو كتابة تعليمات برمجية (Test Scripts) تنفّذ الاختبارات وتقارن النتائج الفعلية بالمتوقعة تلقائياً (Assertions) دون تدخل بشري متكرر.

مثال: دالة اختبار تنشئ طالباً، تختار مقرراً، تنفذ التسجيل، وتتحقق برمجياً من النجاح — ويمكن تشغيلها مئات المرات في ثوانٍ!

⚖️ قاعدة التكامل الهندسي: متى نستخدم كلاً منهما؟

ملاحظة أكاديمية مهمة: الاختبار الآلي لا يلغي الاختبار اليدوي؛ فكلاهما يكمل الآخر لبناء منتج عالي الجودة:

  • نستخدم الاختبار اليدوي: لاكتشاف مشكلات تجربة المستخدم (UX)، تناسق الألوان والخطوط، والاختبار الاستكشافي (Exploratory Testing).
  • نستخدم الاختبار الآلي: للعمليات المتكررة، الحسابات المنطقية، الحالات الحدية الكثيرة، واختبارات الانحدار (Regression) قبل كل إصدار.
  1. عرّف الاختبار اليدوي: قيام شخص بتشغيل البرنامج بنفسه وإدخال البيانات وملاحظة النتائج للتحقق من عمله.
  2. عرّف الاختبار الآلي: كتابة تعليمات برمجية تنفذ خطوات الاختبار وتتحقق من النتائج تلقائياً دون تكرار بشري يدوي.
  3. اذكر ثلاثة فروق بينهما: (1) التنفيذ (بشري مقابل برمجي)، (2) السرعة والتكرار (الآلي أسرع وأسهل عند التكرار)، (3) الاختبار الاستكشافي وتجربة المستخدم (اليدوي أنسب لهما).
  4. هل يمكن الاستغناء عن الاختبار اليدوي؟ ولماذا؟ لا، لأن الحاسوب لا يملك حساً جمالياً أو حدساً بشرياً لتقييم سهولة الاستخدام (Usability) أو استكشاف سيناريوهات غير مبرمجة مسبقاً.
  5. أعط مثالاً على اختبار مناسب للأتمتة: التحقق من دالة حساب الرسوم الدراسية والخصومات لمئات الحالات المختلفة، أو تشغيل اختبارات الانحدار عند كل رفع للكود (Git Push).

🏗️ 3. مستويات الاختبار (Testing Levels) وهرم الاختبارات

لنفترض أننا نبني نظاماً جامعياً يتكون من: واجهة المستخدم، وحدة الطلاب، وحدة المقررات، وحدة التسجيل، قاعدة البيانات، وخدمة الرسائل. نختبر هذا النظام تدريجياً عبر أربعة مستويات رئيسية من الأصغر إلى الأشمل:

1

اختبار الوحدة (Unit Testing)

اختبار أصغر وحدة منطقية في البرنامج (دالة أو ميثود أو كلاس) بصورة معزولة تماماً عن بقية النظام.

مثال: اختبار دالة calculate_fees(3, 100) والتأكد من إرجاع 300.

2

اختبار التكامل (Integration Testing)

اختبار التفاعل والتعاون بين مكونين أو أكثر (مثل اتصال وحدة التسجيل بقاعدة البيانات أو خدمة البريد).

خطواته: استلام رقم الطالب ← التحقق من وجوده ← التحقق من المقرر ← السعة ← الحفظ في DB.

3

اختبار النظام (System Testing)

اختبار النظام المتكامل ككل في بيئة تحاكي الإنتاج للتأكد من استيفائه لجميع المتطلبات الوظيفية وغير الوظيفية.

مثال: هل يستطيع النظام إضافة طالب، إنشاء مقرر، تسجيله، حساب رسومه، وإصدار تقرير؟

4

اختبار القبول (Acceptance Testing)

التحقق النهائي من أن النظام يلبي احتياجات المستخدم الفعلي والجهة المستفيدة وجاهز للاعتماد الرسمي.

مثال: استخدام موظف شؤون الطلاب للنظام للتأكد من مطابقته للوائح وإجراءات الجامعة الفعلية.

unit_test_example.py — مثال اختبار الوحدة لدالة حساب الرسوم 
def calculate_fees(hours, price):
    return hours * price

def test_calculate_fees():
    result = calculate_fees(3, 100)
    assert result == 300
المستوى (Testing Level)ماذا نختبر؟مثال من النظام الجامعي

Integration Testingتفاعل وتعاون مكونين أو أكثروحدة التسجيل مع قاعدة البيانات وخدمة البريد
System Testingالنظام المتكامل ككلإدارة الجامعة الشاملة (طلاب + مقررات + تقارير)
Acceptance Testingتلبية احتياج المستخدم والجهة المستفيدةاعتماد موظف شؤون الطلاب لنظام التسجيل

3.2 هرم الاختبارات التفاعلي (Software Testing Pyramid)

يوضح هرم الاختبارات التوزيع الهندسي الأمثل لحجم الاختبارات في المشروع؛ حيث تقترح Google Testing Blog كتوزيع تعليمي استرشادي: 70% اختبارات وحدة، و20% اختبارات تكامل، و10% اختبارات نهاية إلى نهاية (وهي نسبة استرشادية مرنة وليست قاعدة جامدة لكل المشاريع). انقر على أي طبقة في الهرم لاستكشاف خصائصها:

  1. ما المقصود باختبار الوحدة؟ اختبار أصغر وحدة منطقية في البرنامج (مثل دالة أو ميثود) بصورة مستقلة للتأكد من صحة منطقها.
  2. ما الفرق بين Unit و Integration؟ Unit يختبر دالة واحدة بمعزل عن غيرها، بينما Integration يختبر التفاعل وتبادل البيانات بين مكونين أو أكثر (كالتسجيل وقاعدة البيانات).
  3. متى نستخدم اختبار النظام؟ بعد تكامل جميع الوحدات، لاختبار النظام المتكامل ككل والتحقق من تحقيقه للمتطلبات الوظيفية وغير الوظيفية.
  4. ما الهدف من اختبار القبول؟ التأكد من أن النظام يلبي احتياجات المستخدمين الفعليين وإجراءات العمل الحقيقية للجهة المستفيدة قبل الاعتماد.
  5. لماذا يحتوي هرم الاختبار عادةً على عدد كبير من اختبارات الوحدة؟ لأن اختبارات الوحدة فائقة السرعة، رخيصة الصيانة، معزولة عن الشبكة والواجهات، وتحدد موضع الخلل بدقة متناهية في أجزاء من الثانية.
  6. صنّف اختبار تسجيل طالب في قاعدة البيانات حسب المستوى المناسب: يُصنّف كـ اختبار تكامل (Integration Testing) لأنه يتحقق من التعاون والتفاعل بين وحدة التسجيل وقاعدة البيانات.

🧭 4. اختبار البداية إلى النهاية (End-to-End Testing / E2E)

اختبار البداية إلى النهاية (E2E Testing): هو اختبار يحاكي رحلة المستخدم الحقيقية الكاملة عبر النظام من البداية حتى النهاية، متضمناً الواجهة الأمامية والخلفية وقاعدة البيانات والخدمات المرتبطة، للتأكد من أن السيناريو الكامل يعمل بسلاسة دون انقطاع.

تسلسل رحلة المستخدم الكاملة (7 خطوات) في اختبار End-to-End لنظام تسجيل المقررات

🔗 Integration Testing (اختبار التكامل)

يركّز على التحقق من تفاعل المكونات البرمجية مع بعضها وتبادل البيانات بينها (مثل اتصال خدمة التسجيل بقاعدة البيانات أو واجهة API).

🚶 End-to-End Testing (البداية إلى النهاية)

يركّز على التحقق من رحلة عمل كاملة من منظور المستخدم النهائي عبر الواجهة الحقيقية للنظام من نقطة البداية حتى النتيجة النهائية.

  1. عرّف اختبار البداية إلى النهاية: اختبار يحاكي رحلة المستخدم الحقيقية عبر جميع طبقات النظام من البداية حتى اكتمال العملية للتأكد من عمل السيناريو ككل.
  2. اذكر مثالاً واقعياً عليه: فتح بوابة الطالب، تسجيل الدخول، استعراض المقررات المتاحة، اختيار مقرر، الضغط على تسجيل، والتحقق من ظهور رسالة تأكيد التسجيل.
  3. لماذا يُعتبر مهماً؟ لأنه يكشف المشكلات التي تظهر فقط عند ربط الواجهة بالخادم وقاعدة البيانات في سيناريو استخدام واقعي.
  4. ما الفرق بينه وبين اختبار التكامل؟ اختبار التكامل يفحص التفاعل بين مكونين أو أكثر تقنياً، بينما اختبار E2E يحاكي مسار المستخدم الكامل من البداية إلى النهاية عبر النظام.

🧩 5. نمط Arrange - Act - Assert (AAA)

يُعد نمط AAA المعيار الذهبي لتنظيم بنية كل اختبار وحدة برمجي بحيث يصبح مقروءاً كقصة واضحة من ثلاثة فصول: التجهيز ← التنفيذ ← التحقق.

1️⃣ Arrange — التجهيز

تجهيز البيانات والمدخلات والكائنات والظروف الأولية اللازمة لتنفيذ الاختبار (مثل: hours = 3 و price = 100).

2️⃣ Act — التنفيذ

استدعاء الدالة أو تنفيذ العملية الواحدة التي نريد اختبارها وتخزين ناتجها (مثل: result = calculate_fees(hours, price)).

3️⃣ Assert — التحقق

مقارنة النتيجة الفعلية (Actual) بالنتيجة المتوقعة (Expected) عبر جملة assert result == 300.

🔬 محاكي تنفيذ نمط AAA خطوة بخطوة

جرّب التبديل بين الدالة السليمة والدالة المعيبة، واستعرض مراحل AAA لترى كيف يكشف Assert الخطأ:

✨ الفوائد الخمس لاستخدام نمط AAA

  1. تنظيم الاختبار: فصل واضح بين الإعداد والتنفيذ والفحص.
  2. تسهيل قراءة الشيفرة: أي مبرمج يفهم هدف الاختبار خلال ثوانٍ.
  3. تسهيل اكتشاف الأخطاء: وضوح موضع الخلل عند فشل جملة assert.
  4. تقليل التعقيد: منع تداخل تجهيز البيانات مع التحقق منها.
  5. تسهيل الصيانة: تعديل مدخلات الاختبار دون كسر منطق التحقق.
  1. ماذا تعني AAA؟ تعني Arrange - Act - Assert (التجهيز - التنفيذ - التحقق).
  2. اشرح وظيفة Arrange: تهيئة البيانات والمدخلات والبيئة اللازمة قبل استدعاء الدالة المراد اختبارها.
  3. ما الفرق بين Act و Assert؟ Act ينفذ العملية/الدالة المستهدفة، بينما Assert يتحقق من مطابقة الناتج الفعلي للنتيجة المتوقعة.
  4. اكتب اختباراً بسيطاً باستخدام AAA:
    def test_fees(): hours, price = 3, 100 # Arrange | res = calculate_fees(hours, price) # Act | assert res == 300 # Assert
  5. ما فوائد تنظيم الاختبار بهذه الطريقة؟ تنظيم الاختبار، تسهيل القراءة، تسريع اكتشاف الأخطاء، تقليل التعقيد، وتسهيل الصيانة.

📏 7. الحالات الطبيعية والحدّية وغير الصحيحة (BVA & EP)

تختبئ معظم العيوب البرمجية عند حدود الشروط (مثل استخدام المبرمج > بدلاً من >=). لذا نصمم بيانات الاختبار وفق ثلاثة تصنيفات وتقنيتين عالميتين:

1. الحالة الطبيعية (Normal Case)

إدخال بيانات صحيحة ومعتادة داخل النطاق المسموح (مثل: سعة المقرر 30، وعدد المسجلين 10 ← النتيجة: قبول التسجيل).

2. الحالة الحدية (Boundary Case)

اختبار القيم الواقعة عند الحدود تماماً أو بجوارها مباشرة (مثل: 28 يُقبل، 29 يُقبل الطالب الثلاثون، 30 يُرفض الطالب الحادي والثلاثون).

3. الحالة غير الصحيحة (Invalid Case)

إدخال قيم مخالفة لقواعد النظام (رقم طالب فارغ، ساعات سالبة، مقرر غير موجود، نص بدل رقم، تسجيل مكرر).

7.1 تحليل القيم الحدّية (Boundary Value Analysis - BVA) وتقسيم التكافؤ (Equivalence Partitioning - EP)

📐 تقنية تحليل القيم الحدية (BVA)

إذا كان العمر المسموح به من 18 إلى 60 سنة ($18 \le \text{Age} \le 60$)، نختبر القيم الست الحرجة:

القيمةالتصنيف الحديالحكم
17أقل من الحد الأدنى ($18 - 1$)مرفوض
18الحد الأدنى تماماً ($\text{Min}$)مقبول
19أعلى من الحد الأدنى ($18 + 1$)مقبول
59أقل من الحد الأعلى ($60 - 1$)مقبول
60الحد الأعلى تماماً ($\text{Max}$)مقبول
61أعلى من الحد الأعلى ($60 + 1$)مرفوض

🗂️ تقنية تقسيم التكافؤ (Equivalence Partitioning)

بدلاً من تجربة كل رقم ممكن من 1 إلى 100، نقسّم البيانات إلى فئات تكافؤ تتصرف بنفس الطريقة، ونختار قيمة ممثلة من كل فئة:

  • فئة غير صالحة (أقل من 18): مثل العمر 12 ← مرفوض.
  • فئة صالحة (من 18 إلى 60): مثل العمر 35 ← مقبول.
  • فئة غير صالحة (أكبر من 60): مثل العمر 75 ← مرفوض.

🎛️ مختبر تحليل القيم الحدية وتقسيم التكافؤ التفاعلي

اختر نطاق القاعدة وجرّب قيماً مختلفة لترى تصنيفها العلمي مباشرة:

  1. ما الفرق بين Normal و Boundary و Invalid؟ Normal بيانات اعتيادية صحيحة؛ Boundary قيم عند حدود النطاق أو بجوارها مباشرة؛ Invalid مدخلات مخالفة للقواعد أو النوع.
  2. لماذا نختبر القيم عند الحدود؟ لأن معظم أخطاء المبرمجين في الشروط المنطقية تقع عند الحدود (مثل كتابة < بدل <= أو نسيان الحد الأعلى).
  3. ما المقصود بتحليل القيم الحدية (BVA)؟ تقنية تصميم اختبارات تركز على القيم الواقعة عند الحد الأدنى والأعلى وأقل/أكبر منهما بمقدار وحدة واحدة.
  4. اشرح تقسيم التكافؤ (EP): تقسيم مجال المدخلات إلى مجموعات متكافئة في السلوك (صالحة وغير صالحة) واختيار قيمة ممثلة من كل مجموعة لتقليل عدد الاختبارات دون فقدان الفعالية.
  5. صمّم اختبارات لخاصية تقبل درجات من 0 إلى 100: قيم حدّية: -1 (مرفوض)، 0 (مقبول)، 1 (مقبول)، 99 (مقبول)، 100 (مقبول)، 101 (مرفوض)، وقيمة متوسطة 75 (مقبول).

➕➖ 8. الاختبارات الإيجابية (Positive) والسلبية (Negative)

✅ الاختبار الإيجابي (Positive Testing)

  • يُدخل بيانات صحيحة ومطابقة للشروط.
  • يتوقع نجاح العملية وتنفيذ المسار الطبيعي (Happy Path).
  • مثال: تسجيل طالب مسجل في الجامعة في مقرر مفتوح فيه مقاعد.

🛡️ الاختبار السلبي (Negative Testing)

  • يُدخل بيانات غير صحيحة أو يحاول تنفيذ عملية ممنوعة.
  • يتوقع الرفض المنضبط برسالة خطأ واضحة دون انهيار النظام.
  • مثال: محاولة تسجيل طالب غير موجود أو تسجيله مرتين في المقرر نفسه.

💡 قاعدة جوهرية في الاختبار السلبي

نجاح الاختبار السلبي (PASSED) يعني أن النظام رفض العملية غير المسموحة كما ينبغي! أما إذا قبل النظام البيانات الخاطئة أو انهار فجأة، فهذا يعني فشل الاختبار (FAILED) ووجود عيب يجب إصلاحه.

  1. عرّف الاختبار الإيجابي: التحقق من أن النظام يقبل البيانات الصحيحة وينفذ العملية المطلوبة بنجاح.
  2. عرّف الاختبار السلبي: التحقق من أن النظام يرفض البيانات أو العمليات غير المسموح بها بطريقة سليمة وآمنة.
  3. أعط مثالاً لكل منهما: الإيجابي: تسجيل طالب صحيح في مقرر متاح؛ السلبي: محاولة تسجيل طالب برقم سالب -1.
  4. هل رفض النظام للبيانات الخاطئة يُعتبر نجاحاً للاختبار؟ نعم، يُعدّ نجاحاً للاختبار السلبي لأنه يثبت التزام النظام بقواعد التحقق والحماية.

🎭 9. المحاكاة وعزل الاعتماديات (Mocking, Stubbing & Faking)

9.1 ما المقصود بالاعتمادية (Dependency) والمحاكاة (Mocking)؟

الاعتمادية (Dependency): هي أي خدمة أو مكون خارجي تحتاج إليه الوحدة البرمجية لإتمام عملها؛ مثل: قاعدة البيانات، خدمة البريد الإلكتروني (SMTP)، خدمة الرسائل النصية (SMS)، أو بوابة الدفع الإلكتروني.

المشكلة: ماذا لو تعطل خادم البريد الإلكتروني أو بطؤ الإنترنت أثناء تشغيل اختبارات الوحدة؟ لا نريد أن يفشل اختبار منطق تسجيل الطالب بسبب خادم خارجي! لذا نستخدم المحاكاة (Mocking): أي استبدال المكون الحقيقي بمكون تجريبي وهمي يحاكي سلوكه لعزل الوحدة قيد الاختبار (System Under Test - SUT).

آلية عزل الاعتماديات الخارجية: استبدال خادم البريد بـ Mock وقاعدة البيانات بـ Stub

9.2 مثال برمجي كامل بلغة Python لعزل خدمة البريد الإلكتروني

mock_email_example.py — استبدال خدمة البريد الحقيقية بدالة وهمية 
# الخدمة الحقيقية في الإنتاج:
def send_email(email, message):
    print("Sending real email via SMTP...")

# الدالة المراد اختبارها (تستقبل خدمة البريد كاعتمادية - Dependency Injection):
def register_student(student, course, email_service):
    if course["students"] >= course["capacity"]:
        return False
    course["students"] += 1
    email_service(student["email"], "Registration successful")
    return True

# الاختبار الآلي مع عزل البريد الإلكتروني:
def test_register_student():
    # Arrange
    student = {"email": "student@example.com"}
    course = {"students": 5, "capacity": 30}
    sent_messages = []

    def fake_email(email, message):
        sent_messages.append((email, message))

    # Act
    result = register_student(student, course, fake_email)

    # Assert
    assert result is True
    assert course["students"] == 6
    assert len(sent_messages) == 1

  • منع إرسال رسائل بريد أو SMS حقيقية للطلاب.
  • تجنب إجراء عمليات دفع مالية حقيقية.
  • محاكاة حالات فشل الشبكة أو انقطاع الخادم.
  • تسريع تنفيذ الاختبارات لتعمل في أجزاء من الثانية.
  • عزل الوحدة المراد اختبارها بدقة.

⚠️ متى يجب الحذر من Mocking؟

إذا استخدمنا المحاكاة لكل شيء بإفراط، فقد ننجح في اختبار «نظام وهمي» لا يعكس سلوك النظام الحقيقي! لذلك نحتاج بجانبه إلى اختبارات تكامل (Integration Tests) تتحقق من تعاون المكونات الحقيقية معاً.

  1. عرّف Mocking: استبدال مكون أو خدمة حقيقية بمكون تجريبي يحاكي سلوكها لعزل الوحدة المختبرة والتحقق من تفاعلاتها.
  2. لماذا نستخدم المحاكاة؟ لعزل الوحدة المختبرة، تسريع الاختبارات، تجنب إرسال رسائل أو مدفوعات حقيقية، ومحاكاة أعطال الشبكة.
  3. ما المقصود بالاعتمادية؟ أي مكون أو خدمة خارجية تعتمد عليها الوحدة البرمجية لأداء وظيفتها (مثل قاعدة البيانات أو خادم البريد).
  4. وضّح الفرق بين Mock و Stub و Fake: Mock للتحقق من الاستدعاءات والتفاعلات؛ Stub لإرجاع إجابات محددة مسبقاً؛ Fake تنفيذ مبسط عامل فعلياً داخل الذاكرة.
  5. كيف نختبر خدمة البريد دون إرسال بريد حقيقي؟ بتمرير دالة/كائن بريد وهمي (fake_email) يسجل الرسائل في قائمة ثم نتحقق من محتوى القائمة عبر assert.
  6. ما مخاطر الإفراط في استخدام Mocking؟ قد ينجح الاختبار على سلوك وهمي مفترض بينما يفشل التكامل الحقيقي بين مكونات النظام الفعلية.

🔄 10. اختبارات الانحدار (Regression Testing)

اختبار الانحدار (Regression Testing): هو إعادة تنفيذ مجموعة الاختبارات المناسبة بعد إجراء أي تعديل أو إضافة أو إصلاح على البرنامج، للتأكد من أن التغييرات الجديدة لم تتسبب في إفساد وظائف قديمة كانت تعمل بنجاح سابقاً.

دورة اختبارات الانحدار: حماية الوظائف القائمة (A + B) عند إضافة ميزات جديدة (C) أو إصلاح الأعطال

10.1 مثال عملي: إضافة خصم 10% للطلاب المتفوقين

regression_fees.py — حماية الحالة القديمة واختبار الميزة الجديدة 
# الدالة بعد التعديل (إضافة معامل اختياري discount=0):
def calculate_fees(hours, price, discount=0):
    total = hours * price
    return total - (total * discount / 100)

# 1. اختبار الانحدار: التأكد من أن الحالة القديمة لا تزال تعمل دون تغيير:
def test_normal_fees():
    assert calculate_fees(3, 100) == 300

# 2. اختبار الميزة الجديدة (خصم 10%):
def test_discount_fees():
    assert calculate_fees(3, 100, 10) == 270

10.2 الفرق الأكاديمي بين Regression Testing و Confirmation Testing

اختبار الانحدار (Regression Testing)اختبار التأكيد (Confirmation / Re-testing)
يتأكد من عدم ظهور عيوب جديدة في باقي النظام.يتأكد من إصلاح عيب محدد كان قد اكتُشف سابقاً.
يختبر الوظائف السليمة التي قد تتأثر بالتغيير.يُعيد تنفيذ الحالة التي فشلت بسبب المشكلة الأصلية.
يركّز على الآثار الجانبية (Side Effects).يركّز على نجاح الإصلاح نفسه (Bug Fix).

⏰ المواقف الستة التي تتطلب تنفيذ اختبارات الانحدار

  1. بعد إصلاح خطأ برمجي (Bug Fix).
  2. بعد إضافة ميزة جديدة (New Feature).
  3. بعد تعديل بنية قاعدة البيانات أو استعلاماتها.
  4. بعد تحديث المكتبات والإطارات الخارجية (Dependencies Upgrade).
  5. قبل إطلاق أي إصدار جديد للمستخدمين (Release).
  6. بعد إعادة هيكلة الشيفرة لتحسينها (Refactoring).
  1. عرّف Regression Testing: إعادة تنفيذ الاختبارات السابقة بعد تعديل البرنامج للتأكد من عدم تضرر الوظائف القائمة.
  2. لماذا نعيد تشغيل الاختبارات بعد التعديل؟ لأن تعديل جزء من الشيفرة قد يسبب آثاراً جانبية غير مقصودة في أجزاء أخرى مرتبطة به.
  3. ما الفرق بين Confirmation و Regression؟ Confirmation يتحقق من إصلاح العيب المحدد نفسه، بينما Regression يتحقق من أن بقية وظائف النظام لم تتأثر سلباً بالإصلاح أو التعديل.
  4. اذكر أربعة مواقف تتطلب اختبار الانحدار: بعد إصلاح عيب، بعد إضافة ميزة، بعد تحديث المكتبات، وبعد إعادة هيكلة الشيفرة (Refactoring).
  5. كيف يمكن أتمتة اختبارات الانحدار؟ بكتابتها في حزمة اختبارات (Pytest) وربطها بخط أنابيب CI/CD لتعمل تلقائياً عند كل تعديل في المستودع.

📊 11. تغطية الشيفرة (Code Coverage) وحدودها العلمية

تغطية الشيفرة (Code Coverage): هي مقياس كمي يقيس نسبة أجزاء الشيفرة البرمجية (الأسطر أو الفروع أو الدوال) التي تم تنفيذها فعلياً أثناء تشغيل حزمة الاختبارات.

🧮 المعادلة الرياضية لحساب تغطية الشيفرة

إذا احتوى البرنامج على $100$ سطر قابل للتنفيذ، ونفّذت الاختبارات $80$ سطراً منها على الأقل مرة واحدة:

$$\text{Code Coverage (\%)} = \frac{\text{Executed Lines}}{\text{Total Lines}} \times 100 = \frac{80}{100} \times 100 = 80\%$$

11.1 الأنواع الأربعة لتغطية الشيفرة

1. Statement Coverage

تغطية التعليمات: قياس نسبة الأسطر/التعليمات البرمجية التي نُفّذت مرة واحدة على الأقل.

2. Branch Coverage

تغطية الفروع: قياس هل تم اختبار جميع مسارات القرار المنطقي (True و False) في جمل if / else.

3. Function Coverage

تغطية الدوال: قياس نسبة الدوال (Functions / Methods) التي تم استدعاؤها أثناء الاختبار.

4. Condition Coverage

تغطية الشروط: قياس هل اختُبرت القيم المنطقية المختلفة لكل شرط فرعي داخل التعبيرات المركبة (AND / OR).

11.2 فخ الاعتماد على نسبة التغطية وحدها (لماذا 100% لا تعني صفراً من الأخطاء؟)

coverage_trap.py — مثال يثبت أن 100% Coverage لا يكفي! 
# 1. نقص تغطية الفروع (Branch Coverage):
def check_age(age):
    if age >= 18:
        return "Allowed"
    else:
        return "Rejected"  # إذا اختبرنا age=25 فقط، فلن يُختبر فرع else أبداً!

# 2. تغطية 100% لكن بدون تحقق حقيقي من صحة الناتج:
def multiply(a, b):
    return a + b  # ⚠️ خطأ منطقي: جمع بدلاً من ضرب!

def test_multiply_bad():
    multiply(2, 3)  # تغطية الدالة 100% لكن بدون assert، فينجح الاختبار كذباً!

def test_multiply_good():
    assert multiply(2, 3) == 6  # ✅ هنا يكتشف الاختبار أن 5 != 6!

📈 مختبر تغطية الشيفرة التفاعلي (check_age)

فعّل حالات الاختبار لترى الفرق بين تغطية التعليمات (Statement) وتغطية الفروع (Branch):

  1. عرّف Code Coverage: مقياس يحدد نسبة أجزاء الشيفرة البرمجية التي تم تنفيذها أثناء تشغيل الاختبارات.
  2. كيف نحسب نسبة التغطية؟ بقسمة عدد الأسطر/الأجزاء المنفذة على العدد الكلي وضرب الناتج في 100.
  3. ما الفرق بين Statement Coverage و Branch Coverage؟ Statement يقيس تنفيذ كل سطر برمجي، بينما Branch يقيس تنفيذ جميع مسارات القرار المنطقي (True و False).
  4. لماذا لا تعني تغطية 100% أن البرنامج خالٍ من الأخطاء؟ لأن تنفيذ السطر لا يعني صحة منطقه، وقد تفتقد الاختبارات جمل assert دقيقة أو تغفل حالات حدّية ومتطلبات غير مكتوبة أصلاً.
  5. ما أهمية التحقق من النتائج المتوقعة؟ جمل assert هي التي تحكم فعلياً على صحة سلوك البرنامج ومطابقته للمتطلبات، وبدونها يصبح تشغيل الشيفرة بلا قيمة تقييمية.

🔁 12. الاختبارات القابلة للتكرار والصيانة (Repeatable & Maintainable Tests)

1. الاختبار القابل للتكرار (Repeatable Test)

هو اختبار حتمي (Deterministic) يعطي النتيجة نفسها في كل مرة يُنفذ فيها ما دامت الشيفرة لم تتغير (مثل assert 5 + 3 == 8).

الخطر المقابل — Flaky Tests (الاختبارات غير المستقرة): اختبارات تنجح مرة وتفشل مرة دون تعديل الكود بسبب اعتمادها على إنترنت متذبذب، خادم خارجي، توقيت الساعة، أو قاعدة بيانات مشتركة متغيرة!

2. الاختبار القابل للصيانة (Maintainable Test)

هو اختبار يسهل فهمه وتعديله مع نمو المشروع، ومن خصائصه الست:

  • أسماء دوال وصفية تشرح السلوك المختبر.
  • تركيز كل اختبار على سلوك واحد محدد.
  • استقلالية الاختبارات وعدم اعتماد أحدها على ترتيب تشغيل آخر.
  • استخدام بيانات اختبار معزولة (Fixtures).
  • عدم تكرار شيفرة التجهيز بصورة مبالغ فيها.
  • توفير رسائل فشل واضحة ومفهومة.
naming_best_practice.py — الفرق بين التسمية المبهمة والوصفية
# ❌ تسمية سيئة ومبهمة (لا تخبرك ماذا فشل عند ظهور التقرير):
def test_01():
    pass

# ✅ تسمية احترافية واضحة (توثق القاعدة والنتيجة المتوقعة):
def test_registration_fails_when_course_is_full():
    pass
  1. ماذا تعني Repeatable Tests؟ اختبارات تعطي النتيجة نفسها بثبات في كل مرة تُشغّل فيها تحت الظروف نفسها.
  2. ما المقصود بـ Flaky Tests؟ اختبارات غير مستقرة تتذبذب نتائجها بين النجاح والفشل دون تغيير في شيفرة البرنامج بسبب اعتمادها على عوامل خارجية أو توقيت متغير.
  3. ما صفات الاختبار الجيد؟ قابل للتكرار، سريع، معزول، واضح التسمية، يختبر سلوكاً واحداً، وسهل الصيانة.
  4. لماذا تُعتبر أسماء الاختبارات مهمة؟ لأن اسم الاختبار يعمل كتوثيق حيّ؛ فعندما يفشل في تقرير CI/CD يعرف المطور فوراً أي ميزة أو قاعدة عمل تعطلت دون قراءة كامل الشيفرة.
  5. كيف نقلل اعتماد الاختبارات على الخدمات الخارجية؟ باستخدام تقنيات المحاكاة والعزل (Mocking, Stubbing, Faking) وبيانات اختبار محلية مستقلة.

🧭 13. استراتيجية الاختبار (Test Strategy) والاختبار المبني على المخاطر

🚀 14. الاختبار المستمر (CI/CD Testing)

بدلاً من تأجيل الاختبار حتى نهاية المشروع، ندمج الاختبارات الآلية داخل دورة التطوير اليومية عبر منظومة CI/CD:

  • التكامل المستمر (CI — Continuous Integration): دمج تعديلات المبرمجين في المستودع المركزي باستمرار مع تشغيل البناء (Build) والاختبارات الآلية فوراً لاكتشاف أي تعارض أو عيب مبكراً.
  • التسليم المستمر (CD — Continuous Delivery) أو النشر المستمر (Continuous Deployment): تجهيز النسخة المختبرة للنشر التلقائي أو شبه التلقائي على بيئات الاختبار والإنتاج بثقة عالية.

⚙️ محاكي خط أنابيب CI/CD التفاعلي (GitHub Actions Pipeline)

اختبر سيناريو رفع تعديل برمجي (git push) على دالة تسجيل الطلاب في الحالتين التاليتين:

🏆 الفوائد الخمس لتشغيل الاختبارات داخل CI/CD

  1. اكتشاف الأخطاء خلال دقائق من كتابتها وقبل تراكمها.
  2. منع وصول التعديلات المكسورة (Breaking Changes) إلى النسخة الرئيسية.
  3. تسريع وتيرة إصدار التحديثات والميزات للمستخدمين.
  4. توفير وقت الفريق بإلغاء التشغيل اليدوي المتكرر.
  5. رفع مستوى الثقة في استقرار كل إصدار جديد.
  1. ما المقصود بـ CI؟ التكامل المستمر (Continuous Integration): دمج الشيفرة باستمرار وبناؤها واختبارها آلياً.
  2. ما المقصود بـ CD؟ التسليم المستمر (Continuous Delivery) أو النشر المستمر (Continuous Deployment).
  3. ما دور الاختبارات في CI/CD؟ تعمل كبوابة جودة آلية (Quality Gate) تتحقق من سلامة البناء والوظائف بعد كل تعديل قبل السماح بالنشر.
  4. ماذا يحدث إذا فشلت الاختبارات؟ يتوقف خط الأنابيب (Pipeline Fails)، يُرسل تنبيه فوري للمطور، ويُمنع دمج أو نشر التغيير المعيب.

🛡️ 15. الاختبارات الوظيفية وغير الوظيفية (Functional & Non-Functional Testing)

لا تقتصر استراتيجية الاختبار الاحترافية على Unit و Integration و E2E؛ بل تشمل عشرة أنواع متكاملة تجيب عن سؤالين كليين: ماذا يفعل النظام؟ (وظيفي) و كيف وبأي جودة يعمل؟ (غير وظيفي):

#نوع الاختبارالتصنيفالسؤال الذي يجيب عنه + مثال تطبيقي
1Functional Testing
(الاختبار الوظيفي)		وظيفيهل الوظيفة تعمل وفق المتطلبات؟
مثال: هل يستطيع الطالب تسجيل مقرر وحساب رسومه؟
2Non-Functional Testing
(الاختبار غير الوظيفي)		غير وظيفيما مستوى جودة تشغيل النظام؟
يشمل الأداء، الأمان، سهولة الاستخدام، والتوافق.
3Performance Testing
(اختبار الأداء)		غير وظيفيهل النظام سريع ومستجيب؟
مثال: قياس زمن الاستجابة عند دخول 1,000 مستخدم معاً.
4Load Testing
(اختبار الحمل)		غير وظيفيهل يتحمل النظام الحمل المتوقع؟
محاكاة عدد الطلاب المتوقع وقت بدء التسجيل الفصلي (مثلاً 5,000 مستخدم).
5Stress Testing
(اختبار الإجهاد)		غير وظيفيماذا يحدث تحت ضغط شديد يتجاوز السعة؟
تحديد نقطة الانهيار (Breaking Point) وكيفية تعافي النظام بعدها.
6Security Testing
(اختبار الأمان)		غير وظيفيهل البيانات والصلاحيات محمية؟
مثال: هل يستطيع طالب الاطلاع على درجات طالب آخر أو تعديلها؟
7Usability Testing
(اختبار سهولة الاستخدام)		غير وظيفيهل الواجهة مفهومة وسهلة للطالب؟
قياس وضوح القوائم والرسائل وسلاسة إتمام المهام.
8Compatibility Testing
(اختبار التوافق)		غير وظيفيهل يعمل في بيئات وأجهزة مختلفة؟
تجربة البوابة على Chrome و Firefox والهواتف الذكية.
9Smoke Testing
(اختبار الدخان)		فحص أوليهل الوظائف الأساسية للنسخة تعمل؟
فحص سريع وسطي للتأكد من أن النسخة الجديدة قابلة لمزيد من الاختبار.
10Sanity Testing
(اختبار السلامة المحدود)		فحص مركّزهل التعديل المحدد يعمل بصورة معقولة؟
فحص ضيق ومركّز بعد إصلاح بسيط للتأكد من سلامة الجزء المعدّل.
  1. ما الفرق بين Functional و Non-Functional؟ الوظيفي يتحقق من «ماذا يفعل النظام» (تنفيذ الوظائف)، بينما غير الوظيفي يتحقق من «كيف يعمل» (السرعة، الأمان، سهولة الاستخدام، التوافق).
  2. عرّف Load Testing: اختبار قدرة النظام واستقراره تحت حجم حمل متوقع من المستخدمين والطلبات المتزامنة.
  3. ما الفرق بين Load و Stress Testing؟ Load يختبر الحمل الطبيعي/المتوقع، بينما Stress يرفع الضغط إلى مستويات قصوى تتجاوز القدرة المعتادة لاكتشاف نقطة الانهيار وسلوك التعافي.
  4. ما الهدف من Security Testing؟ اكتشاف الثغرات وحماية البيانات ومنع الوصول غير المصرح به (مثل منع طالب من رؤية درجات زميله).
  5. ما الفرق بين Smoke و Sanity Testing؟ Smoke فحص سطحي عريض للوظائف الأساسية لقبول البناء؛ أما Sanity فحص ضيق وعميق نسبياً يركز على جزء محدد بعد تعديل أو إصلاح صغير.
  6. لماذا نحتاج إلى اختبار التوافق (Compatibility)؟ لضمان عمل النظام بصورة صحيحة عبر مختلف المتصفحات وأنظمة التشغيل وأحجام شاشات المستخدمين.

def register_student(student, course, registrations):
    if not isinstance(student, dict):
        return "INVALID_STUDENT"
    if not isinstance(course, dict):
        return "INVALID_COURSE"
    if not isinstance(registrations, list):
        return "INVALID_REGISTRATIONS"

    student_id = student.get("id")
    course_id = course.get("id")
    capacity = course.get("capacity")
    students = course.get("students")

    if not isinstance(student_id, int) or isinstance(student_id, bool) or student_id <= 0:
        return "INVALID_STUDENT"
    if not isinstance(course_id, int) or isinstance(course_id, bool) or course_id <= 0:
        return "INVALID_COURSE"

    if (not isinstance(capacity, int) or isinstance(capacity, bool) or capacity < 0):
        return "INVALID_CAPACITY"
    if (not isinstance(students, int) or isinstance(students, bool) or students < 0):
        return "INVALID_COUNT"
    if students > capacity:
        return "INVALID_COUNT"

    if any(not isinstance(item, tuple) or len(item) != 2 for item in registrations):
        return "INVALID_REGISTRATIONS"
    if any(sid == student_id and cid == course_id for sid, cid in registrations):
        return "ALREADY_REGISTERED"
    if students >= capacity:
        return "COURSE_FULL"

    registrations.append((student_id, course_id))
    course["students"] += 1
    return "SUCCESS"

  11. تغطية الشيفرة (Code Coverage) تقيس نسبة التنفيذ ولا تقيس صحة البرنامج وحدها.
  12. الاختبارات الجيدة قابلة للتكرار (Repeatable) والصيانة (Maintainable).
  13. استراتيجية الاختبار (Test Strategy) تحدد أسلوب الاختبار وأولوياته ومعاييره.
  14. منظومة CI/CD تسمح بتشغيل الاختبارات تلقائياً أثناء التطوير.
  15. الاختبارات الوظيفية وغير الوظيفية تكمل بعضها لبناء منتج موثوق.
