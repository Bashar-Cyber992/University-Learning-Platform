✨ 1. ما المقصود بالشيفرة النظيفة (Clean Code)؟

الشيفرة النظيفة Clean Code: هي شيفرة مصدرية مكتوبة بأسلوب واضح ومنظم وبسيط، يستطيع أي مطور آخر (أو أنت نفسه بعد أشهر) قراءتها وفهم غرضها وتعديلها واختبارها بسرعة وبأقل قدر من الغموض.

⚖️ تنبيه منهجي: لا يوجد رقم سحري واحد للنظافة!

لا يوجد مقياس رقمي عالمي موحد يعرّف الشيفرة النظيفة بنسبة 100%؛ بل هي مجموعة مبادئ وممارسات هندسية راسخة يُنظر إليها في سياق لغة البرمجة وحجم المشروع واتفاق الفريق.

1.1 مثال تطبيقي بلغة Python: قبل التنقيح وبعده

❌ قبل: شيفرة تعمل لكنها مبهمة (Python) 
def c(a, b, d):
    return a * b - d

x = c(10, 5, 3)
print(x)  # Output: 47
✅ بعد: شيفرة نظيفة تشرح نفسها (Python) 
def calculate_total(price, quantity, discount):
    return price * quantity - discount

total = calculate_total(10, 5, 3)
print(total)  # Output: 47

المخرجان متطابقان (47)، لكن في النسخة الثانية تتضح المعادلة فوراً دون تخمين معنى c, a, b, d, x.

1.2 الفوائد الست للشيفرة النظيفة

1

سهولة القراءة

فهم منطق البرنامج وسياقه خلال دقائق بلا ألغاز.

2

سهولة الصيانة

تعديل الأجزاء المعنية بأقل آثار جانبية غير متوقعة.

3

سهولة الاختبار

الدوال المنظمة والمركزة تسهل بناء اختبارات الوحدة الآلية.

4

تقليل الأخطاء

الوضوح يكشف الثغرات المنطقية مبكراً أثناء المراجعة.

5

سهولة العمل الجماعي

اندماج المطورين الجدد في الفريق بسرعة وسلاسة.

6

تقليل التكلفة مستقبلاً

انخفاض زمن التطوير وإضافة الميزات على مدى عمر المشروع.

1.3 تنبيه شائع: الشيفرة النظيفة ≠ الشيفرة القصيرة

❌ مختصرة لكنها غامضة (JS)
const r = a => a.filter(x => x > 50).length;
✅ أوضح وأسهل للفريق (JS)
function countPassingGrades(grades) {
    return grades.filter(grade => grade > 50).length;
}

الهدف هو الوضوح والبساطة المناسبة لا مجرد تقليص عدد الأسطر أو حروف الأسماء.

  1. إذا كان البرنامج يعمل اليوم، فلماذا أهتم بنظافة الشيفرة؟ لأن معظم التكلفة الزمنية في عمر البرمجيات تذهب لقراءة الشيفرة وفهمها وتعديلها لاحقاً لا لكتابتها أول مرة.
  2. هل تعني النظافة تقليل عدد الأسطر بأقصى ما يمكن؟ لا؛ الاختزال المفرط يضر بالوضوح. المهم البساطة المفهومة.
  3. كيف أقيس وضوح الشيفرة عملياً؟ بمدى سرعة مطور آخر في فهم وظيفتها وموضع التعديل المطلوب دون سؤال كاتبها.
  4. هل تؤخر الكتابة النظيفة المبرمج؟ قد تستغرق دقائق إضافية للتسمية والتنظيم، لكنها توفر ساعات وأياماً في التصحيح والتطوير اللاحق.
  5. هل تتغير المبادئ باختلاف لغة البرمجة؟ الجوهر واحد (الوضوح، التسمية، عدم التكرار، صغر المسؤولية) مع اختلاف الأعراف الشكلية للغة.

🏷️ 2. معايير تسمية المتغيرات والدوال والفئات (Naming)

تخيّل كتاباً تعليمياً بلا عناوين فصول، وكل شخصياته تحمل أرقاماً مثل شخصية 1 وشخصية 2! التسمية في الشيفرة هي أسرع طريق للفهم أو للارتباك. يجب أن يجيب الاسم عن: ما هذا؟ لماذا وُجد؟ وكيف يُستخدم؟

2.1 تسمية المتغيرات (أسماء دالة على المعلومة)

تجنب الرموز العامة مثل x = 25 واختر اسماً يعكس السياق مثل student_count = 25 أو product_price = 25.

الاسم الغامض ❌الاسم الواضح ✅لماذا الاسم الجديد أفضل؟
xstudent_countيوضح فوراً أن القيمة تمثل عدد الطلاب.
ddiscount_amountيميز مبلغ الخصم عن التاريخ (date) أو البيانات (data).
ncustomer_nameيؤكد أنه اسم نصي وليس رقماً (number).
vinvoice_totalيحدد بوضوح أنه إجمالي الفاتورة المالية.

ℹ️ استثناء مقبول

استخدام أسماء مختصرة مثل i أو x مقبول فقط في المعادلات الرياضية المعروفة أو عدادات الحلقات القصيرة جداً (for i in range(5)) حيث يكون السياق بديهياً.

2.2 تسمية الدوال (أفعال) والفئات (أسماء كيانات)

تبدأ الدوال بأفعال تصف عملها (calculate_average()، validate_email()، send_notification()، get_student_by_id())، بينما تحمل الفئات أسماء كيانات (Student، Invoice، PaymentProcessor، StudentReport).

Java — دالة بفعل واضح وحماية القسمة
public static double calculateAverage(double totalGrades, int studentCount) {
    if (studentCount == 0) {
        return 0;
    }
    return totalGrades / studentCount;
}
C++ — فئة باسم كيان (أفضل من Data)
class Student {
public:
    string name;
    double grade;
};

2.4 أعراف الكتابة الشائعة و 2.5 تجنب الأسماء المضللة

snake_case

شائع في متغيرات ودوال Python (مثال: calculate_total).

camelCase

شائع لمتغيرات ودوال Java وJavaScript (مثال: calculateAverage).

PascalCase

شائع لأسماء الفئات في Java وC# وغيرها (مثال: StudentReport).

هذه أعراف شائعة وليست قواعد جامدة عابرة لكل اللغات؛ والمهم اتباع دليل أسلوب المشروع (Style Guide). واحذر الأسماء المضللة لأن الاسم الخاطئ يخدع المطور أكثر من الاسم المختصر!

❌ اسم مضلل (نص في اسم عددي)
student_count = "أحمد"
✅ اسم صادق ومطابق للبيانات
student_name = "أحمد"
  1. متى يُسمح باستخدام حروف مثل i أو x؟ في الحلقات القصيرة جداً أو المعادلات الرياضية المعروفة فقط.
  2. لماذا تبدأ الدوال بأفعال؟ لأن الدالة تمثل إجراءً أو حساباً يُنفَّذ، بينما المتغير والفئة يمثلان بيانات أو كيانات.
  3. ما خطورة الاسم المضلل؟ يزرع فهماً خاطئاً بثقة زائفة فيقود لتعديلات وافتراضات خاطئة.
  4. هل اختيار أسلوب التسمية يؤثر على المترجم؟ غالباً لا يمنع التشغيل، لكنه يلتزم بعرف اللغة ودليل المشروع ليسهل الفهم المشترك.
  5. كيف أوحد أسماء مشروع غير منسق؟ عبر اعتماد Style Guide واضح في التسمية والالتزام به في كل إضافة وتنقيح.

🔁 3. تقليل التكرار والتعقيد: مبدأ DRY

ينص مبدأ DRY — Don't Repeat Yourself على ألا يتكرر المنطق أو المعرفة دون حاجة بحيث يكون لها مصدر واحد واضح (ولا يُقصد به حظر أي تشابه لفظي عابر). لاحظ التوفير في Python وJavaScript:

❌ 3.1 المشكلة: تكرار معادلة 15%
price1 = 100
total1 = price1 + (price1 * 0.15)
print(total1)

price2 = 200
total2 = price2 + (price2 * 0.15)
print(total2)

price3 = 300
total3 = price3 + (price3 * 0.15)
print(total3)
✅ 3.2 الحل: Python (نسبة 15% مثال افتراضي)
def calculate_total_with_tax(price):
    tax_rate = 0.15
    return price + (price * tax_rate)

print(calculate_total_with_tax(100))  # 115.0
print(calculate_total_with_tax(200))  # 230.0
print(calculate_total_with_tax(300))  # 345.0
✅ نفس المبدأ بلغة JavaScript
function calculateTotalWithTax(price) {
    const taxRate = 0.15;
    return price + (price * taxRate);
}

console.log(calculateTotalWithTax(100)); // 115
console.log(calculateTotalWithTax(200)); // 230
console.log(calculateTotalWithTax(300)); // 345

3.3 تقليل التداخل والتعقيد الشرطي و 3.4 متى لا ندمج المتشابه؟

❌ تداخل شرطي زائد
def can_register(age, has_permission):
    if age >= 18:
        if has_permission:
            return True
        else:
            return False
    else:
        return False
✅ تبسيط مباشر (عند تطابق قاعدة العمل)
def can_register(age, has_permission):
    return age >= 18 and has_permission

⚠️ متى يكون توحيد الشيفرة المتشابهة قراراً خاطئاً؟ (3.4)

إذا تشابهت معادلة خصم الطالب وخصم الموظف اليوم (10% مثلاً)، فلا تدمجهما قسراً في دالة واحدة بعلم شرطي! لأن كل منهما يمثل سياسة عمل مستقلة قد تتغير منفصلة مستقبلاً، ودمجهما يخلق اقتراناً ضاراً وتعقيداً غير مبرر.

  1. هل يعني DRY منع تكرار أي حرف أو جملة؟ لا؛ بل منع تكرار المنطق والقواعد التي يجب أن يكون لها مصدر موثوق واحد.
  2. ما خطر نسخ نفس المعادلة في أكثر من مكان؟ نسيان تحديث بعض النسخ عند تغير القاعدة فتظهر نتائج متناقضة.
  3. متى أترك شيفرتين متشابهتين منفصلتين؟ عند اختلاف سبب تغيرهما وقواعد العمل الخاصة بكل منهما (مثل خصم الطالب مقابل خصم الموظف).
  4. هل اختصار الشرط إلى سطر واحد أفضل دائماً؟ فقط إذا بقي واضحاً ومباشراً؛ فالوضوح أولى من الاختصار الزائد.
  5. كيف يدعم DRY الاختبار وإعادة الاستخدام؟ تجميع المنطق في دالة واحدة يتيح اختبارها وإعادة استدعائها بأمان.

🧩 4. مبدأ المسؤولية الواحدة (Single Responsibility Principle - SRP)

يُعد مبدأ SRP أول مبادئ SOLID: ينبغي أن يكون لكل وحدة أو فئة مسؤولية واضحة محددة وسبب منطقي واحد للتغيير (وللدوال: مهمة رئيسية واضحة). تخيّل موظفاً واحداً يمسك المحاسبة + الاستقبال + الصيانة + الرواتب؛ أي تغيير في أحدها يربك كل البقية!

شكل (2): التحول من فئة متعددة المهام إلى 3 وحدات متماسكة وفق SRP
❌ قبل: StudentManager (خلط مسؤوليات)
class StudentManager:
    def calculate_average(self, grades):
        return sum(grades) / len(grades)  # ينهار على []!

    def send_email(self, email, message):
        print(f"Sending email to {email}: {message}")

    def save_report(self, report):
        print("Saving report:", report)
✅ بعد: 3 فئات متخصصة + حماية القائمة الفارغة
class GradeCalculator:
    def calculate_average(self, grades):
        if not grades:
            return 0
        return sum(grades) / len(grades)

class EmailService:
    def send_email(self, email, message):
        print(f"Sending email to {email}: {message}")

class ReportRepository:
    def save_report(self, report):
        print("Saving report:", report)

✨ الفوائد الخمس لتطبيق SRP وتنبيه الاعتدال

يمنحك SRP: (1) تقليل الترابط (Coupling)، (2) اختبارات مركزة في عزلة، (3) تعديلات أكثر أماناً، (4) وضوح مكان الميزات الجديدة، (5) سهولة تقسيم العمل بين الفريق.

ملاحظة: أوامر الطباعة هنا للتبسيط التعليمي (في الإنتاج توجد اتصالات بريدية وقواعد بيانات ومعالجة أخطاء)، كما يجب تجنب الإفراط في تقسيم كل سطر إلى فئة مستقلة.

  1. هل تضم الفئة في SRP دالة واحدة فقط؟ لا؛ بل كل الدوال المرتبطة بالمسؤولية المتماسكة نفسها.
  2. ما المقصود بسبب واحد للتغيير؟ تغير الفئة استجابةً لجهة أو سياسة عمل واحدة فقط دون تأثرها ببقية الطبقات.
  3. ما أضرار المبالغة في تفكيك الفئات؟ تشتيت المنطق وكثرة الملفات وتعقيد التتبع بلا فائدة حقيقية.
  4. كيف يسرّع SRP كتابة اختبارات الوحدة؟ يُمكّنك من اختبار الحساب المالي أو الدرجات دون الحاجة لتهيئة خادم بريد أو قاعدة بيانات.
  5. ما موقع SRP ضمن SOLID؟ هو الحرف الأول S وأساس التنظيم الكائني النظيف.

⚡ 5. كتابة دوال واضحة ومحددة المسؤولية

الدالة الواضحة تؤدي مهمة محددة، تفصل المنطق الحسابي عن الطباعة والتخزين، وتكشف أي خلل منطقي مخفي. تأمل المثال التالي لحساب طلب شراء:

❌ دالة متضخمة + ثغرة منطقية خفية
def process_order(order):
    total = 0
    for item in order["items"]:
        total += item["price"] * item["qty"]
    if order["customer_type"] == "student":
        total = total * 0.90
    if order["total"] > 500:  # ⚠️ خطأ: تفحص order["total"] لا total!
        total = total * 0.95
    print("Saving order to database...")
    print("Sending confirmation email...")
    return total
✅ بعد: دوال مقسمة بمسؤوليات صافية
def calculate_subtotal(items):
    return sum(item["price"] * item["qty"] for item in items)

def apply_student_discount(total, customer_type):
    return total * 0.90 if customer_type == "student" else total

def apply_large_order_discount(total):
    return total * 0.95 if total > 500 else total

def calculate_order_total(order):
    subtotal = calculate_subtotal(order["items"])
    after_student = apply_student_discount(subtotal, order["customer_type"])
    return apply_large_order_discount(after_student)

🔎 دقة هندسية: الخلل المنطقي الخفي وسياسة الخصم المتسلسل

في الدالة الأولى كان السطر order["total"] > 500 يفحص قيمة قديمة مخزنة في القاموس لا total المحسوب! وبعد التفكيك طُبقت سياسة الخصم المتسلسل بوضوح (حساب خصم الطلب الكبير على المبلغ بعد خصم الطالب) مع عزل أوامر الطباعة والحفظ.

كما تُعد دالة calculateAverage(double total, int count) في Java (بإرجاع 0 عند count <= 0) مثالاً تبسيطياً، بينما قد ترفع الأنظمة الحقيقية استثناءً للمدخلات السالبة.

🚨 5 علامات تحذيرية تدل أن الدالة أكبر من اللازم

  • تجمع بين مهام غير مترابطة (حساب + طباعة + تخزين + بريد).
  • تحوي تداخلات شرطية وحلقات متعددة المستويات.
  • تحتاج لتعليقات داخلية مثل "الجزء الأول..." و"الجزء الثاني..." لتقسيمها نظرياً.
  • يصعب اختبار خطوة حسابية واحدة منها بمعزل عن البقية.
  • تضم كتلاً يمكن استخراجها لدوال بأسماء واضحة (دون التقيد برقم أسطر جامد).
  1. هل يوجد عدد أسطر ثابت لا يجوز تجاوزه في الدالة؟ لا؛ المعيار هو التماسك والوضوح وتحديد المسؤولية.
  2. لماذا نفصل الحساب عن الطباعة والتخزين؟ لإمكانية إعادة استخدام منطق الحساب في الاختبارات أو واجهات مختلفة.
  3. كيف أختار ما أستخرجه لدالة جديدة؟ كل خطوة فرعية لها هدف مستقل يمكن تسميتها بفعل معبّر يرفع وضوح الدالة الأم.
  4. ما أثر الإفراط في تقطيع الدوال السطرية؟ يصبح القارئ مضطراً للقفز بين عشرات الدوال لتتبع خطوة تافهة.
  5. ما فائدة فحص count <= 0 في أول الدالة؟ حماية البرنامج من القسمة على صفر وتوضيح الحالات الحدية مبكراً.

👃 6. اكتشاف الروائح البرمجية (Code Smells)

الرائحة البرمجية Code Smell: تشبه الشق الظاهر على جدار مبنى سليم ظاهرياً؛ لا تعني وجود خطأ نحوي يوقف التشغيل الآن، لكنها تشير إلى ضعف محتمل في البنية والتصميم يضاعف صعوبة الصيانة مستقبلاً.

الرائحة البرمجيةالمظهرالمشكلة المترتبةالعلاج المقترح
1. الدالة الطويلة
Long Method		دالة تؤدي مهام متفرقة كثيرة.صعوبة الفهم والاختبار الجزئي.استخراج دوال صغيرة مركزة.
2. الشيفرة المكررة
Duplicated Code		نسخ نفس المنطق في مواضع عدة.خطأ التعديل وتناقض السلوك.التوحيد في دالة مشتركة (DRY).
3. كثرة المعاملات
Long Parameter List		استقبال الدالة 6–10 معاملات.نسيان الترتيب وصعوبة الاستدعاء.التجميع في كائن أو تقسيم الواجهة.
4. الفئة المتضخمة
Large Class		فئة تجمع مسؤوليات متباعدة.تضخم الترابط وهشاشة التعديلات.توزيع المهام وفق SRP.
5. التداخل العميق
Deep Nesting		شروط وحلقات متراكمة للداخل.إرهاق ذهني وفقدان المسار.العودة المبكرة (Guard Clauses).

🎯 6.3 أولوية المعالجة (Prioritization)

نُوازن بين الأثر الفعلي وتكلفة الإصلاح: فالشيفرة القديمة المستقرة التي لا تتغير ولا تسبب أعطالاً أولويتها منخفضة مقارنة بالوحدات كثيرة التعديل وتكرار الأخطاء.

  1. هل الرائحة البرمجية خطأ يوقف التشغيل؟ لا؛ يعمل البرنامج لكنها مؤشر ضعف بنيوي يصعب الصيانة.
  2. لماذا يتعب التداخل العميق القارئ؟ لأنه يُلزم الذهن بالاحتفاظ بعدة شروط متداخلة معاً لفهم شرط التنفيذ.
  3. كيف تعالج العودة المبكرة الشروط؟ تستبعد الحالات المستثناة في الأعلى فيسير المسار السليم بشكل مستقيم.
  4. كيف نحل كثرة المعاملات؟ نجمع المترابط منها في كائن Parameter Object أو نقسم الدالة.
  5. ما معيار ترتيب أولوية التنظيف؟ البدء بالشيفرة كثيرة التعديل والأعطال بدلاً من الشيفرة الثابتة غير المستخدمة في التطوير الحالي.

function calculateAverage(grades) {
    if (!grades || grades.length === 0) {
        return 0;
    }
    const total = grades.reduce((sum, grade) => sum + grade, 0);
    return total / grades.length;
}

function determineResult(average) {
    return average >= 50 ? "Pass" : "Fail";
}

const grades = [80, 70, 90];
const average = calculateAverage(grades);

GradeCalculator.java — التطبيق النظيف في Java
public class GradeCalculator {
    public static double calculateAverage(double[] grades) {
        if (grades == null || grades.length == 0) {
            return 0;
        }
        double total = 0;
        for (double grade : grades) {
            total += grade;
        }
        return total / grades.length;
    }

    public static String determineResult(double average) {
        return average >= 50 ? "Pass" : "Fail";
    }

    public static void main(String[] args) {
        double[] grades = {80, 70, 90};
        double avg = calculateAverage(grades);
        System.out.println("Average: " + avg);
        System.out.println("Result: " + determineResult(avg));
    }
}

  4. تبسيط شروط الرصيد + التفعيل + العنوان: باستخدام Guard Clauses (عودة مبكرة عند فقد أي شرط).
  5. استبدال تعليق بديهي بشيفرة تشرح نفسها: نقل حلقة الجمع تحت دالة باسم calculate_total_price(prices) وحذف التعليق الزائد.
  6. 4 اختبارات وحدة بعد التعديل: حالة طبيعية، حالة حدية (صفر)، حالة فراغ/قسمة على صفر، ومدخل سالب غير صالح.
  1. لماذا لا يلتزم البعض بالشيفرة النظيفة رغم معرفتهم بأهميتها؟ بسبب ضغط التسليم السريع وتراكم الدَّين التقني وغياب المراجعة.
  2. متى تكون إعادة الهيكلة ضرورية جداً؟ قبل توسعة وحدة معقدة أو في مواطن الأعطال المتكررة؛ وتؤجل في الأجزاء المستقرة غير المتغيرة.
  3. هل يضر الإفراط في التقسيم؟ نعم (Over-engineering)، فيشتت التدفق بين عشرات الملفات والدوال التافهة.
  4. كيف نوازن بين السرعة والجودة؟ بتطبيق عادات سريعة يومية (التسمية وتجنب النسخ) بدلاً من تراكم فوضى مكلفة.
  5. هل تكفي أدوات مثل Ruff/SonarLint للحكم على النظافة؟ لا؛ تكشف الشكل وبعض الأنماط لكنها لا تقيم سلامة المعمارية وسياق الأسماء.

📝 تلخيص المحاضرة في 8 نقاط ذهبية + الخاتمة

  1. الشيفرة النظيفة ضرورة هندسية تخفض أخطاء الصيانة وتسرّع العمل الجماعي.
  2. التسمية المعبرة تجعل الكود مفهوماً دون تخمين وتمنع الأخطاء المضللة.
  3. مبدأ DRY يوحد المنطق مع الحذر من دمج سياسات عمل مختلفة.
  4. مبدأ SRP يمنح كل وحدة مسؤولية واضحة وسبب تغيير واحد.
  5. الدوال الصغيرة تفصل الحساب عن الطباعة والتخزين وتسهل الاختبار.
  6. الروائح البرمجية (Code Smells) تنبهنا لضعف التصميم قبل تضخمه.
  7. إعادة الهيكلة تحسن البنية دون تغيير السلوك وتحميها اختبارات الوحدة.
  8. التعليق الجيد يوضح لماذا بينما التوثيق يشرح الاستخدام والقيود.
