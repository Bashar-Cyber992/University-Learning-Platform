💡 السؤال الجوهري في المعمارية الأمنية للبرمجيات

عندما نقوم بتشغيل برنامج على جهاز الحاسوب، فإننا نمنحه القدرة على تنفيذ تعليمات برمجية، وقد يحتاج هذا البرنامج إلى الوصول إلى ملفات الجهاز، أو الشبكة، أو الذاكرة، أو قواعد البيانات.

لكن ماذا يحدث إذا كان البرنامج غير موثوق؟ وماذا لو احتوى على تعليمات خبيثة تحاول حذف الملفات أو سرقة المعلومات أو الوصول إلى موارد لا تخصه؟

هنا تظهر واحدة من أهم أفكار المعمارية الأمنية: لا ينبغي أن يحصل البرنامج على جميع صلاحيات النظام لمجرد أنه يعمل عليه. ومن هذا المبدأ ظهرت فكرة بيئة التنفيذ المعزولة (Sandbox)، وتُعد Java Sandbox من أشهر دراسات الحالة التاريخية لفهم كيفية بناء حدود أمنية حول البرامج.

📦 1. ما المقصود ببيئة التنفيذ المعزولة (Sandbox)؟

1.1 التعريف العلمي والتفسير المبسط

📘 المحتوى الأصلي للمحاضرة

التعريف العلمي: بيئة التنفيذ المعزولة (Sandbox) هي بيئة تشغيل أمنية يتم فيها تنفيذ برنامج أو شيفرة برمجية ضمن حدود محددة من الصلاحيات والموارد، بحيث لا يستطيع البرنامج الوصول إلى موارد النظام الأخرى إلا وفق ما تسمح به قواعد وسياسات الأمان.

بمعنى أبسط: هي مساحة آمنة نسبياً نضع فيها البرنامج، ونحدد مسبقاً ما يستطيع فعله وما يُمنع عليه فعله.

🏖️ لماذا سُميت Sandbox (صندوق الرمل)؟

كلمة Sandbox تعني حرفياً صندوق الرمل. تخيّل طفلاً يلعب داخل صندوق رمل في حديقة؛ يستطيع اللعب وتحريك الرمل وبناء الأشكال بحرية داخل الصندوق، لكنه لا يستطيع الوصول إلى كل ما يوجد خارج حدود الصندوق. بنفس الطريقة، يستطيع البرنامج داخل البيئة المعزولة تنفيذ المهام المسموحة له، لكنه لا يحصل تلقائياً على حق الوصول إلى جميع موارد الجهاز.

1.2 مثال واقعي: برنامج عرض ملف PDF محمّل من الإنترنت

لنفترض أن لدينا برنامجاً يقوم بعرض ملف PDF تم تحميله من الإنترنت. عند تحليل احتياجات هذا البرنامج أمنياً نجد تبايناً واضحاً بين ما يحتاجه لأداء وظيفته وما يشكل خطراً إن مُنح له:

✅ الموارد التي يحتاج إليها البرنامج (مسموحة)

  • قراءة ملف PDF المحدد الذي اختاره المستخدم فقط.
  • استخدام مساحة محددة من الذاكرة (RAM) لمعالجة الصفحات.
  • عرض الصور والنصوص على نافذة الشاشة.
  • استخدام المعالج (CPU) لتنفيذ عمليات العرض.

🚫 الموارد التي لا يحتاج إليها البرنامج (محظورة)

  • حذف أو تعديل ملفات نظام التشغيل.
  • قراءة كلمات المرور المحفوظة في المتصفح أو النظام.
  • الوصول إلى ملفات المستخدم الخاصة دون إذن صريح.
  • تثبيت برامج أخرى في الخلفية.
  • التحكم في الكاميرا أو الميكروفون دون تصريح.

1.3 المبادئ الأمنية الخمسة التي تحققها بيئة Sandbox

المبدأ الأمني المصطلح الإنجليزي التفسير الوظيفي داخل Sandbox
العزل Isolation فصل البرنامج وبيئة تنفيذه عن بقية موارد النظام غير المصرح بها.
أقل صلاحية Least Privilege إعطاء البرنامج أقل قدر ممكن من الصلاحيات اللازمة لإنجاز مهمته فقط.
التحكم في الوصول Access Control تحديد من يستطيع الوصول إلى الموارد وما نوع العملية (قراءة، كتابة، تنفيذ).
تقليل الأضرار Damage Limitation الحد من تأثير البرنامج وحجم الخسائر عند حدوث خلل برمجي أو اختراق.
الاحتواء Containment إبقاء آثار تنفيذ الشيفرة ضمن نطاق محدود ومضبوط يسهل مراقبته وإيقافه.

⚠️ ملاحظة أكاديمية جوهرية

Sandbox ليست ضماناً مطلقاً للأمان، وإنما آلية دفاعية لتقليل المخاطر وتحديد نطاق تأثير البرنامج؛ إذ قد تحتوي طبقة العزل نفسها على ثغرات أو إعدادات خاطئة ما لم تُدعّم بطبقات حماية متكاملة.

1.4 أمثلة حقيقية على تطبيق مبدأ Sandbox عبر لغات البرمجة والأنظمة الحديثة

🔬 الإثراء المعماري وتطبيقات الواقع

مبدأ Sandbox هو مبدأ أمني عام وليس خاصاً بلغة Java وحدها؛ ويُطبَّق اليوم في لغات البرمجة ومنصات التشغيل الكبرى كما يوضح الجدول والبطاقات التالية:

اللغة التقنية المستخدمة للعزل مثال تطبيقي واقعي مثال برمجي مبسط
Java JVM (تاريخياً Applet Sandbox) عزل تطبيقات Java وتحليل البيانات try { ... }
Python Docker تشغيل كود الطالب في منصات التعليم print("Hello")
JavaScript Chrome Sandbox عزل صفحات ومحتوى الويب في المتصفح alert('Hi')
C / C++ seccomp تقييد استدعاءات النظام لبرامج النظام int main(){}
C# AppContainer تطبيقات Windows المعزولة Console.WriteLine();
PHP Docker + PHP-FPM مواقع الاستضافة المشتركة <?php echo 'Hi'; ?>
Go gVisor / Docker الخدمات السحابية وخدمات الويب fmt.Println("")
Rust WASM / seccomp الإضافات البرمجية (Plugins) fn main() {}

🌐 Chrome Sandbox

يعزل كل تبويب وصفحة ويب في عملية مقيدة الصلاحيات لمنع الشيفرات الضارة في المواقع من الوصول إلى ملفات نظام المستخدم.

🐳 Docker Containers

يشغّل تطبيقات متعددة على الخادم نفسه بشكل معزول من حيث نظام الملفات والشبكة واستهلاك الموارد.

🏆 منصة DOMjudge

تُستخدم في مسابقات البرمجة لتشغيل حلول الطلاب بلغات متعددة داخل حاويات معزولة تمنع الغش أو تخريب الخادم.

⚖️ 2. لماذا تحتاج البرمجيات إلى حدود للصلاحيات والموارد؟

📘 المحتوى الأصلي للمحاضرة

2.1 المشكلة الأمنية الأساسية في أنظمة التشغيل

توفّر أنظمة التشغيل موارد كثيرة ومتنوعة للبرامج التي تعمل عليها، من أبرزها:

1. الملفات والمجلدات
File System
2. الذاكرة الرئيسية
Memory / RAM
3. المعالج
CPU Cycles
4. الشبكة والاتصالات
Network Sockets
5. الإدخال والإخراج
I/O Devices
6. قواعد البيانات
Databases
7. الأجهزة الطرفية
Camera / Mic / USB

إذا حصل كل برنامج على صلاحية الوصول إلى جميع هذه الموارد دون قيود، فإن أي خطأ برمجي (Bug) أو سلوك خبيث قد يؤدي إلى أضرار كارثية على البيانات والنظام.

2.2 مبدأ أقل صلاحية (Principle of Least Privilege - PoLP)

📐 التعريف العلمي لمبدأ أقل صلاحية (PoLP)

مبدأ أقل صلاحية (Principle of Least Privilege - PoLP): هو مبدأ أمني جوهري ينص على أن كل مستخدم أو برنامج أو عملية يجب أن تحصل فقط على الحد الأدنى من الصلاحيات الضرورية لإنجاز مهمتها المحددة، ولا شيء أكثر من ذلك.

مثال توضيحي: تطبيق مبدأ أقل صلاحية على برنامج آلة حاسبة (Calculator)

هل يحتاج برنامج آلة حاسبة بسيطة إلى حذف الملفات، أو قراءة مستندات المستخدم، أو الاتصال بالإنترنت؟ الإجابة: لا. منح هذه الصلاحيات يُعد مخالفة صريحة لمبدأ أقل صلاحية:

المورد في النظام الصلاحية المطلوبة لآلة حاسبة التعليل الأمني
الذاكرة (Memory) مسموح ضمن الحدود ضرورية لتخزين الأرقام والعمليات الحسابية مؤقتاً.
المعالج (CPU) مسموح ضروري لتنفيذ العمليات الرياضية.
ملفات النظام ممنوع لا علاقة لعمليات الجمع والطرح بتعديل ملفات النظام.
كلمات المرور ممنوع بيانات شديدة الحساسية لا تحتاجها الوظيفة الحسابية.
الشبكة والإنترنت غير مطلوبة / ممنوع منعها يقطع الطريق أمام تسريب بيانات المستخدم للخارج.
الكاميرا والميكروفون ممنوع حماية خصوصية المستخدم من التجسس.

2.3 المخاطر الخمسة المترتبة على غياب حدود الصلاحيات

1

تسريب المعلومات (Information Disclosure)

قد يستطيع البرنامج قراءة ملفات خاصة أو كلمات مرور أو بيانات شخصية لا تخصه.

2

تخريب الملفات (Data Tampering / Destruction)

قد يحذف البرنامج ملفات مهمة أو يعدّل محتواها أو يشفّرها كما في برمجيات الفدية.

3

استهلاك الموارد (Resource Exhaustion)

قد يستهلك البرنامج الذاكرة أو المعالج بشكل مفرط فيؤدي إلى توقف النظام (DoS).

4

الانتشار غير المصرح به (Lateral Movement)

قد يتواصل مع أنظمة وخوادم أخرى عبر الشبكة لنشر العدوى أو مهاجمة أجهزة مجاورة.

5

تصعيد الصلاحيات (Privilege Escalation)

قد يستغل ثغرة برمجية للحصول على امتيازات مدير النظام (Admin / Root).

النتيجة: حدود الصلاحيات لا تحمي سرية البيانات فقط، بل تحمي استقرار النظام وموثوقيته وتوافره أيضاً.

🔒 3. كيفية عزل الشيفرة عن الموارد غير المصرح بها

📘 المحتوى الأصلي للمحاضرة

3.1 مفهوم عزل الشيفرة (Code Isolation) وعناصره الأربعة

عزل الشيفرة (Code Isolation): هو منع الشيفرة البرمجية من التأثير في أجزاء النظام أو الوصول إلى موارده خارج النطاق المسموح لها. مثلاً، إذا قمنا بتشغيل برنامج Java غير موثوق، فقد نسمح له بقراءة ملف تقارير محدد، ونمنعه من قراءة بقية ملفات الجهاز.

1

البرنامج (Program)

الشيفرة البرمجية أو الوحدات المراد تنفيذها.

2

بيئة التنفيذ (Runtime)

البيئة التي تنفّذ الشيفرة وتراقب عملياتها الحساسة.

3

سياسة الأمان (Security Policy)

مجموعة القواعد التي تحدد الصلاحيات المسموحة والمحظورة.

4

الموارد (Resources)

الملفات، الشبكة، الذاكرة، النظام، والأجهزة الطرفية.

3.2 تصنيف الموارد: الاستخدام المسموح مقابل الاستخدام المحظور

المورد الاستخدام المسموح (ضمن الحدود) الاستخدام المحظور (خارج النطاق)
الملفات (Files) قراءة ملف محدد أو مجلد عمل مخصص. قراءة جميع ملفات النظام أو كلمات المرور.
الشبكة (Network) الاتصال بخادم محدد ومنفذ مصرح به. الاتصال العشوائي بأي خادم خارجي.
الذاكرة (Memory) استخدام ذاكرة العملية المخصصة. تجاوز حدود الذاكرة أو قراءة ذاكرة عمليات أخرى.
النظام (System) تنفيذ العمليات الحسابية المصرح بها. إيقاف النظام أو تنفيذ أوامر نظام غير مصرح بها.
الأجهزة (Devices) استخدام جهاز مصرح به عند الحاجة. التحكم بالكاميرا أو الميكروفون دون إذن صريح.

3.3 مثال برمجي مبسط: كيف كانت سياسات الأمان تُكتب تاريخياً؟

لنفترض أن لدينا برنامج Java يحتاج إلى قراءة ملف اسمه report.txt فقط، ولا يُسمح له بقراءة passwords.txt. في النموذج الأمني التقليدي، كانت السياسة تُصاغ كالآتي:

legacy_java.policy — مثال توضيحي للسياسة التاريخية 
grant {
    permission java.io.FilePermission "/data/report.txt", "read";
};

🚨 تنبيه أكاديمي وتقني مهم جداً

هذا المثال يوضح فكرة السياسة القديمة لفهم المعمارية تاريخياً، وليس إعداداً صالحاً لتفعيل Sandbox في Java 24 أو الإصدارات الأحدث؛ لأن Security Manager أصبح معطلاً بصورة دائمة منذ Java 24 (وفق وثائق Oracle الرسمية).

3.4 مسار اتخاذ القرار عند طلب الوصول إلى مورد + مثال برنامج تصحيح الاختبارات

مخطط تدفق قرار التحكم في الوصول عند محاولة البرنامج استخدام مورد في النظام

🎓 مثال من الحياة العملية: برنامج تصحيح اختبارات الطلاب في الجامعة

لنفترض أن جامعة تستخدم برنامجاً آلياً لتصحيح اختبارات الطلاب:

  • يحتاج البرنامج إلى: قراءة ملفات إجابات الطلاب، معالجة الإجابات، وتخزين الدرجات في قاعدة بيانات مخصصة.
  • ولا يحتاج إلى (ويُمنع عنه): قراءة ملفات رواتب الموظفين، الوصول إلى كلمات مرور النظام، حذف قواعد بيانات أخرى، أو التحكم في أجهزة الجامعة.

⚙️ 4. دور بيئة تشغيل Java (JVM) في تنفيذ البرامج

📘 المحتوى الأصلي للمحاضرة

4.1 ما هي JVM؟ والتمييز بين JDK و JRE و JVM

آلة Java الافتراضية (JVM — Java Virtual Machine): هي بيئة تنفيذ مسؤولة عن تشغيل Java Bytecode، وتوفر خدمات أساسية مثل إدارة الذاكرة وتنفيذ التعليمات والتحقق من سلامة بعض العمليات أثناء التنفيذ.

المصطلح الاسم الكامل المعنى والدور التقني
JDK Java Development Kit مجموعة أدوات تطوير برامج Java (تضم المترجم javac والأدوات + JRE).

4.3 ما العلاقة بين JVM والأمان؟ (4 ركائز أساسية)

تؤدي JVM دوراً مهماً في أمن Java عبر أربع آليات، لكن لا ينبغي اعتبارها وحدها صندوق حماية كاملاً:

1. التحقق من Bytecode

تمنع Bytecode Verifier تنفيذ التعليمات المشوّهة أو التي تخالف قواعد آلة Java الافتراضية وتجاوز المكدس.

2. إدارة الذاكرة التلقائية

تدير الذاكرة وتوفر Garbage Collection، مما يقلل أخطاء المؤشرات وتجاوز سعة المخزن المؤقت (Buffer Overflow).

3. نظام الأنواع (Type Safety)

تفرض قواعد صارمة للتحقق من أنواع البيانات ومنع التحويل القسري غير الآمن للذاكرة.

4. تحميل الفئات (Class Loading)

ينظم نطاقات الأسماء (Namespaces) ويفصل الفئات القادمة من مصادر محلية أو بعيدة.

4.4 مكونات الأمان التاريخية الخمسة في Java Sandbox

المكوّن التاريخي الوظيفة الأمنية في النموذج الكلاسيكي
Class Loaderتحميل الفئات وتنظيم نطاقات الأسماء وفصل مصادر الشيفرة.

Security Managerفرض قيود الوصول إلى الموارد الحساسة قبل تنفيذ العمليات.

ملاحظة مهمة: هذه المكونات لا تعمل اليوم جميعها بالطريقة التاريخية نفسها، خصوصاً بعد تعطيل Security Manager بصورة دائمة في Java 24.

📜 5. مفهوم الصلاحيات والسياسات الأمنية في بيئات Java

📘 المحتوى الأصلي للمحاضرة

5.1 تعريف الصلاحيات (Permissions) والسياسة الأمنية (Security Policy)

  • الصلاحيات (Permissions): هي الحقوق الدقيقة التي تُمنح للشيفرة البرمجية لتنفيذ عمليات محددة على موارد النظام (مثل قراءة ملف، الكتابة في ملف، الاتصال بعنوان شبكي، أو قراءة خصائص النظام).
  • السياسة الأمنية (Security Policy): هي مجموعة قواعد مكتوبة تحدد العمليات التي يُسمح للشيفرة بتنفيذها والموارد التي يمكنها الوصول إليها؛ كأن تسمح للبرنامج بقراءة مجلد التقارير وتمنعه من تعديل ملفات النظام.

5.2 عناصر النموذج الأمني التاريخي في Java (Java 1.2 Security Model)

1. مصدر الشيفرة (Code Source)

المكان أو المصدر الذي جاءت منه الفئة البرمجية، مثل ملف محلي (Local File) أو عنوان URL بعيد أو شهادة توقيع رقمي.

2. نطاق الحماية (Protection Domain)

نطاق يجمع الفئات القادمة من نفس المصدر ويربطها بمجموعة من الخصائص والصلاحيات الأمنية المحددة لها.

3. الصلاحية (Permission)

كائن يمثّل الحق الممنوح في تنفيذ عملية محددة على مورد بعينه.

4. السياسة (Policy)

القاعدة التي تربط كل مصدر شيفرة أو نطاق حماية بالصلاحيات المسموحة له.

5. مدير الأمان (Security Manager)

الآلية التاريخية التي كانت تفحص العمليات الحساسة قبل السماح بتنفيذها وفق سياسة الأمان المعتمدة.

5.3 أنواع الصلاحيات التاريخية في Java

نوع الصلاحية في Java وظيفتها ونطاق تحكمها
FilePermissionالتحكم في الوصول إلى الملفات والمجلدات (قراءة، كتابة، حذف، تنفيذ).
SocketPermissionالتحكم في إنشاء واستقبال اتصالات الشبكة والمنافذ.
PropertyPermissionالتحكم في قراءة أو تعديل خصائص النظام (System Properties).
RuntimePermissionالتحكم في بعض عمليات بيئة التشغيل الحساسة (مثل إيقاف JVM).
ReflectPermissionالتحكم في بعض عمليات الانعكاس البرمجي (Reflection) والوصول للأعضاء الخاصة.

مثال تطبيقي على صياغة سياسة قديمة:

property_read.policy — صياغة تاريخية
grant {
    permission java.util.PropertyPermission "java.version", "read";
};

تذكير تقني: هذا المثال يوضّح منح صلاحية قراءة خاصية إصدار Java ضمن نموذج السياسات التاريخي، ولا يفرض حماية فعلية في JDK 24 وما بعدها بعد تعطيل Security Manager نهائياً.

🔍 6. تحليل حدود الحماية وافتراضات التصميم والتطور حتى Java 24

📘 المحتوى الأصلي للمحاضرة

هل توفر Java Sandbox حماية مطلقة؟ الإجابة القاطعة: لا. لأن المهندس الأمني المحترف لا يكتفي بمعرفة كيف تعمل آلية الحماية، بل يجب أن يحلل متى تفشل ولماذا. الأمان الحقيقي يعتمد على الدفاع متعدد الطبقات (Defense in Depth).

6.1 حدود الحماية الخمسة والمخاطر المحتملة

1. الثغرات البرمجية (Vulnerabilities)

قد توجد ثغرات في JVM نفسها أو المكتبات المستخدمة يستغلها المهاجم لتجاوز القيود الأمنية.

2. الصلاحيات الزائدة (Excessive Permissions)

منح البرنامج صلاحيات أوسع من حاجته (كقراءة جميع ملفات المستخدم) يضاعف حجم الضرر عند الاختراق.

3. استهلاك الموارد (Resource Exhaustion)

قد ينفذ البرنامج حلقة لا نهائية أو يستهلك الذاكرة والمعالج؛ ويجب التمييز بين التحكم بصلاحيات الوصول والتحكم باستهلاك الموارد فهما مشكلتان مختلفتان.

4. تجاوز حدود العزل (Sandbox Escape)

استغلال ثغرة في طبقة العزل للخروج من البيئة المقيدة والوصول إلى نظام التشغيل المضيف.

5. الشيفرة الأصلية (Native Code / JNI)

استخدام واجهة JNI (Java Native Interface) للتعامل مع شيفرة C/C++ يضيف مخاطر لا تغطيها ضمانات JVM المعتادة.

6.2 افتراضات التصميم الأمني التاريخية

الافتراض التصميمي المقصود به في التصميم التاريخي نقطة الضعف الواقعية
سلامة JVMأن بيئة التنفيذ تعمل بصورة صحيحة وخالية من العيوب.قد تظهر ثغرات تنفيذية في JVM نفسها.
صحة Bytecodeأن الشيفرة تمر عبر التحقق المطلوب بدقة.ثغرة في المدقق قد تسمح بتعليمات غير آمنة.
موثوقية Class Loaderأن تحميل الفئات لا يسمح بتجاوز حدود الثقة.تعقيد محملات الفئات المخصصة قد يسبب ثغرات.
صحة السياسة الأمنيةأن الصلاحيات محددة بصورة صحيحة ودقيقة.الأخطاء البشرية في كتابة السياسات شائعة.
سلامة فحص الصلاحياتأن كل العمليات الحساسة تخضع للفحص.نسيان فحص نقطة استدعاء واحدة يكسر الحماية.
عدم وجود ثغرات قابلة للاستغلالافتراض خلو المنظومة من نقاط الاستغلال.افتراض تصميمي لا يمكن ضمانه بصورة مطلقة.

6.3 لماذا لا تكفي JVM وحدها لعزل البرامج؟

⚠️ تشارك مساحة العملية والذاكرة داخل JVM الواحدة

تعمل JVM داخل عملية نظام تشغيل (OS Process)، وقد تتشارك البرامج التي تعمل داخل JVM نفسها في مساحة العملية والذاكرة وبعض الموارد. فإذا تم اختراق برنامج أو استغلال ثغرة في طبقة التنفيذ، فقد تتأثر برامج أخرى ضمن العملية نفسها. ولهذا توصي إرشادات Oracle باستخدام عمليات JVM منفصلة لعزل الشيفرات غير الموثوقة عن الشيفرات الموثوقة، مع الاستفادة من آليات العزل على مستوى نظام التشغيل والحاويات.

🚨 السيناريو الأول: دون عزل أمني (بيئة غير آمنة)

عند تشغيل البرنامج الخبيث بصلاحيات مفتوحة دون حدود عزل، تصبح جميع الموارد الحساسة مكشوفة لخطر الوصول المباشر:

  • ملفات الطلاب ← خطر الوصول والسرقة
  • كلمات المرور ← خطر الوصول والاختراق
  • الشبكة الخارجية ← خطر تسريب البيانات
  • ملفات التقارير ← خطر الحذف والتخريب
توضيح أكاديمي: هذا يبيّن مخاطر منح صلاحيات واسعة، ولا يعني أن كل عملية خبيثة ستنجح تلقائياً، لكن غياب العزل يزيل الحواجز الوقائية.

🛡️ السيناريو الثاني: مع العزل الأمني (بيئة مقيدة الصلاحيات)

عند وضع البرنامج داخل حدود العزل الأمني وتطبيق مبدأ أقل صلاحية:

  • قراءة الملفات المصرح بها فقط ← مسموح
  • إنشاء التقارير في المجلد المحدد ← مسموح
  • قراءة كلمات المرور ← محظور ومرفوض
  • إرسال البيانات للخارج وحذف التقارير ← محظور ومرفوض
مقارنة بصرية بين تشغيل برنامج غير موثوق دون عزل مقابل تشغيله داخل بيئة مقيدة الصلاحيات

📝 الخلاصة العلمية للمحاضرة (7 مبادئ ختامية)

توضح دراسة Java Sandbox أن الأمن البرمجي لا يتحقق بمجرد كتابة برنامج صحيح نحوياً، وإنما يحتاج إلى معمارية تحدد حدود الثقة والصلاحيات والموارد:

  1. يجب ألا يحصل البرنامج إلا على الصلاحيات الضرورية لإنجاز مهمته.
  2. يجب عزل الشيفرة غير الموثوقة عن الموارد الحساسة في النظام.
  3. تلعب JVM دوراً مهماً في سلامة تنفيذ Bytecode وإدارة الذاكرة.
  4. كانت Security Manager والسياسات الأمنية من مكونات نموذج Java Sandbox التاريخي.
  5. لا توجد بيئة معزولة توفر حماية مطلقة وحدها.
  6. يجب مراعاة التطورات التقنية لكل إصدار من Java (خاصة تعطيل Security Manager في Java 24).
  7. تعتمد الحلول الحديثة على عزل العمليات والحاويات وآليات نظام التشغيل والآلات الافتراضية بحسب مستوى المخاطر.

الرسالة الأساسية: نفّذ ما تحتاج إليه، ولا تسمح بما لا تحتاج إليه — Execute only what is necessary. Access only what is permitted.

🎓 10. أسئلة المناقشة والتقييم (الفهم، التحليل، والتطبيق)

اضغط على كل قسم لاستعراض الأسئلة الواردة في المحاضرة مع الإجابات النموذجية المفصلة:

  1. ما المقصود ببيئة التنفيذ المعزولة Sandbox؟ هي بيئة تشغيل أمنية يُنفذ فيها البرنامج ضمن حدود محددة من الصلاحيات والموارد بحيث لا يصل إلى موارد النظام الأخرى إلا وفق قواعد وسياسات الأمان.
  2. لماذا لا ينبغي منح البرامج جميع صلاحيات النظام؟ لأن أي خطأ برمجي أو شيفرة خبيثة في البرنامج قد تؤدي إلى تسريب البيانات، تخريب الملفات، استهلاك الموارد، الانتشار عبر الشبكة، أو تصعيد الصلاحيات.
  3. ما الفرق بين العزل (Isolation) والتحكم في الوصول (Access Control)؟ العزل يفصل البرنامج وبيئة تنفيذه عن بقية موارد النظام، بينما التحكم في الوصول يحدد القواعد الدقيقة لمن يستطيع الوصول إلى مورد معين ونوع العملية المسموحة (قراءة/كتابة).
  4. ما المقصود بمبدأ أقل صلاحية (Least Privilege)؟ هو منح كل مستخدم أو برنامج أو عملية الحد الأدنى من الصلاحيات الضرورية لإنجاز مهمته المحددة فقط.
  5. ما دور JVM في تنفيذ برامج Java؟ هي الآلة الافتراضية المسؤولة عن تحميل الفئات، التحقق من سلامة Bytecode، إدارة الذاكرة، وتنفيذ التعليمات عبر المفسر أو مترجم JIT فوق نظام التشغيل.
  6. ما الفرق بين Bytecode و Source Code؟ Source Code هو الشيفرة المكتوبة بلغة Java القابلة للقراءة البشرية (.java)، بينما Bytecode هو الشيفرة الوسيطة المترجمة بواسطة javac (.class) التي تفهمها وتنفذها JVM.
  7. ما وظيفة Class Loader؟ تحميل الفئات البرمجية (.class) إلى الذاكرة وتنظيم نطاقات الأسماء وفصل الفئات القادمة من مصادر مختلفة.
  8. ما وظيفة Bytecode Verifier؟ فحص سلامة تعليمات Bytecode والتأكد من صحة أنواع البيانات والالتزام بقواعد التنفيذ الآمن قبل تشغيلها في JVM.
  1. لماذا لا تُعتبر JVM وحدها وسيلة كافية لعزل البرامج غير الموثوقة؟ لأنها تعمل داخل عملية نظام تشغيل واحدة وقد تتشارك البرامج داخلها في مساحة العملية والذاكرة، كما أن أي ثغرة في JVM أو الشيفرة الأصلية قد تكسر القيود البرمجية؛ لذا يلزم العزل على مستوى العمليات ونظام التشغيل.
  2. ماذا يمكن أن يحدث إذا منحنا برنامجاً صلاحية قراءة جميع ملفات النظام؟ قد يقرأ كلمات المرور المحفوظة، مفاتيح التشفير، بيانات المستخدمين والطلاب الحساسة، وملفات إعدادات النظام ثم يسربها إلى خادم خارجي.
  3. كيف يمكن أن يتسبب استهلاك الذاكرة في تهديد أمن النظام؟ قد ينفذ البرنامج حلقة لا نهائية أو يخصص كميات ضخمة من الذاكرة فيستنزف موارد الخادم ويؤدي إلى توقف النظام والخدمات الأخرى (Denial of Service).
  4. ما الفرق بين Security Manager التاريخي وآليات العزل الحديثة؟ Security Manager آلية برمجية داخل JVM تعتمد على ملفات Policy وفحص الاستدعاءات داخل العملية؛ أما العزل الحديث فيعتمد على نواة نظام التشغيل والحاويات والآلات الافتراضية (Process Isolation, Docker, namespaces, seccomp) لعزل العمليات والموارد فعلياً.
  5. لماذا تم تعطيل Security Manager في Java 24؟ لأنه أصبح نموذجاً معقداً وصعب الصيانة وعرضة للأخطاء في إعداد السياسات، ولم يعد يوفر الحماية الشاملة المطلوبة مقارنة بتقنيات العزل الحديثة على مستوى نظام التشغيل والحاويات.
  6. ما المخاطر التي قد تنتج عن استخدام JNI مع شيفرة غير موثوقة؟ تتيح واجهة JNI استدعاء شيفرة أصلية مكتوبة بلغات مثل C/C++ تعمل خارج حدود حماية JVM وإدارة الذاكرة الآمنة، مما يسمح بتجاوز قيود النظام والتلاعب المباشر بالذاكرة.
  7. متى يكون من الأفضل تشغيل الشيفرة غير الموثوقة داخل JVM منفصلة؟ عندما نحتاج إلى فصل مساحة الذاكرة والعملية عن التطبيق الرئيسي الحساس بحيث لا يؤدي تعطل أو اختراق الشيفرة غير الموثوقة إلى التأثير على التطبيق الأساسي.
  1. السؤال الأول (تحديد الموارد لبرنامج قراءة ملفات الطلاب):
    • 5 موارد مسموحة: (1) قراءة مجلد/ملف درجات الطلاب، (2) الكتابة في مجلد التقارير، (3) حصة محددة من الذاكرة RAM، (4) حصة محددة من المعالج CPU، (5) إخراج النتائج للشاشة أو سجل التشغيل.
    • 5 موارد محظورة: (1) ملفات كلمات المرور، (2) ملفات نظام التشغيل، (3) الاتصال بالإنترنت/الشبكة الخارجية، (4) الكاميرا والميكروفون، (5) قواعد بيانات الرواتب أو الموارد البشرية.
  2. السؤال الثاني (تصميم سياسة تمنع الوصول لملفات كلمات المرور): تُبنى السياسة على مبدأ المنع الافتراضي (Default Deny) بحيث يُمنح البرنامج صلاحية القراءة فقط لمسار مجلد الدرجات المحدد (/data/grades/) عبر مستخدم نظام محدود الصلاحيات وصلاحيات ملفات ACL/chmod ونظام ملفات معزول (Read-only mount في الحاوية)، فلا يرى مسار كلمات المرور أصلاً.
  3. السؤال الثالث (منع الاتصال بالإنترنت باستخدام وسائل العزل الحديثة): تشغيل البرنامج داخل حاوية Docker مع خيار تعطيل الشبكة (--network none)، أو عبر Linux Network Namespaces وجدار حماية النظام لمنع إنشاء أي مقبس شبكي (Socket) خارجي.
  4. السؤال الرابع (هل يمكن الاعتماد على ملف Policy لتطبيق قيود Security Manager في Java 24؟): لا يمكن مطلقاً؛ لأن Security Manager أصبح معطلاً بصورة دائمة منذ إصدار JDK 24، ولن يقوم ملف java.policy بفرض أي حظر على الملفات أو الشبكة، بل يجب الاعتماد على عزل العمليات ونظام التشغيل والحاويات.

🗂️ 11. بطاقات الاستذكار التفاعلية (16 بطاقة)

انقر على أي بطاقة لقلبها واختبار تذكّرك للمصطلحات والمفاهيم الأساسية في المحاضرة الرابعة:

Sandbox
(بيئة التنفيذ المعزولة)انقر لقلب البطاقة ↺
بيئة تشغيل أمنية ينفذ فيها البرنامج ضمن حدود محددة من الصلاحيات والموارد وفق قواعد وسياسات الأمان.
Principle of Least Privilege
(مبدأ أقل صلاحية - PoLP)انقر لقلب البطاقة ↺
منح كل مستخدم أو برنامج أو عملية الحد الأدنى من الصلاحيات الضرورية لإنجاز مهمته فقط.
Isolation vs. Containment
(العزل والاحتواء)انقر لقلب البطاقة ↺
العزل: فصل البرنامج عن الموارد غير المصرح بها.
الاحتواء: إبقاء آثار التنفيذ ضمن نطاق محدود.
JDK vs. JRE vs. JVM
(بيئة Java)انقر لقلب البطاقة ↺
JDK: أدوات التطوير والمترجم.
JRE: بيئة التشغيل.
JVM: الآلة الافتراضية التي تنفذ Bytecode.
Bytecode (.class)
(الشيفرة الوسيطة)انقر لقلب البطاقة ↺
التعليمات الوسيطة الناتجة عن ترجمة ملف .java بواسطة javac لتنفذها آلة JVM.
Class Loader
(محمّل الفئات)انقر لقلب البطاقة ↺
مكون في JVM يحمّل الفئات المطلوبة وينظم نطاقات الأسماء ويفصل الفئات حسب مصادرها.
Bytecode Verifier
(مدقق الشيفرة الوسيطة)انقر لقلب البطاقة ↺
يفحص سلامة تعليمات Bytecode وصحة أنواع البيانات والالتزام بقواعد التنفيذ الآمن قبل تشغيلها.
Protection Domain
(نطاق الحماية)انقر لقلب البطاقة ↺
نطاق يجمع الفئات القادمة من نفس Code Source ويربطها بالصلاحيات الأمنية الممنوحة لها.
Security Manager & Java 24
(مدير الأمان التاريخي)انقر لقلب البطاقة ↺
آلية فحص الصلاحيات في نموذج Java التاريخي؛ أصبحت مهملة في Java 17 ومعطلة بصورة دائمة في Java 24.
Resource Exhaustion
(استنزاف الموارد)انقر لقلب البطاقة ↺
استهلاك مفرط للذاكرة أو المعالج (مثل حلقة لا نهائية)، ويختلف عن مشكلة التحكم في صلاحيات الوصول.
Sandbox Escape
(تجاوز حدود العزل)انقر لقلب البطاقة ↺
استغلال ثغرة في طبقة العزل للخروج من البيئة المقيدة والوصول إلى موارد النظام المضيف.
JNI (Native Code Risk)
(الشيفرة الأصلية)انقر لقلب البطاقة ↺
واجهة تسمح لـ Java باستدعاء كود C/C++ خارج حماية JVM، مما يضيف مخاطر أمنية إضافية.
Process Isolation
(عزل العمليات)انقر لقلب البطاقة ↺
تشغيل الشيفرة غير الموثوقة في عملية نظام تشغيل مستقلة وداخل JVM منفصلة عن التطبيق الحساس.
Containers (Docker)
(الحاويات)انقر لقلب البطاقة ↺
تقنية حديثة لتغليف وتشغيل التطبيقات مع تقييد نظام الملفات والشبكة وحصص الذاكرة والمعالج.
Linux seccomp & AppArmor
(آليات نظام التشغيل)انقر لقلب البطاقة ↺
أدوات على مستوى نواة نظام التشغيل لتصفية استدعاءات النظام (Syscalls) وتقييد وصول البرامج للموارد.
Core Lecture Motto
(الرسالة الأساسية)انقر لقلب البطاقة ↺
نفّذ ما تحتاج إليه، ولا تسمح بما لا تحتاج إليه.
Execute only what is necessary. Access only what is permitted.
